# ⟦L6:variables.product.prodname_vscode_shortname⟧ でのカスタム指示の使用

カスタム指示を使用すると、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供できます。すべてのプロンプトで同じ内容を繰り返すのではなく、Markdown ファイルにガイダンスを保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている1つの規則から始めます。[Agent Customizations エディター](⟦U75⟧)で指示を作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、および設定については、[カスタム指示リファレンス](⟦U76⟧)を参照してください。

指示はモデルをガイドするものです。準拠を保証したり、テスト、コードレビュー、セキュリティ制御の代わりになったりするものではありません。[インラインサジェスト](⟦U77⟧)を入力している間は適用されません。

## プロジェクト指示の開始

リポジトリのルートを開き、使用する予定の[エージェントハーネスを選択します](⟦U78⟧)。ハーネスによって、どの指示ファイルが読み取られるかが決まります。たとえば、⟦L7:variables.product.prodname_copilot_short⟧ セッションで Claude モデルを選択しても、Claude ハーネスには切り替わりません。

最初のセットアップでは、テストセッションからコミットされていない指示にアクセスできるようにするため、新しいワークツリーではなく現在のフォルダーで作業を行います。

### プロジェクト指示の作成

1. コマンドパレット（⟦I19⟧）から **Chat: Open Customizations** を実行して Agent Customizations エディターを開き、**Instructions** タブを選択します。

1. プロジェクト指示ファイルを追加するには、**Workspace** の横にある ⟦I20⟧ を選択し、⟦I21⟧ や ⟦I22⟧ など、ハーネスに対して提供されているプロジェクト指示ファイルを選択します。エディターによってワークスペースにファイルが作成されるか、既存のファイルが開きます。

   リポジトリにすでにプロジェクト指示ファイルがある場合は、競合するコピーを作成するのではなく、既存のファイルを開いてください。

1. 繰り返されている問題に対処するいくつかの具体的なルールを追加します。たとえば、Node.js API プロジェクトでは次の指示を使用できます。パスとテストコマンドを、リポジトリで機能するものに置き換えてください。

   ⟦C1⟧

1. ファイルを保存します。これらのプロジェクト指示ファイルにはフロントマターは必要ありません。

#### ファイルを直接作成する

Agent Customizations エディター以外の場所でファイルを作成したい場合は、ハーネスでサポートされているプロジェクト指示ファイルを使用してください。以下のパスはリポジトリのルートからの相対パスです。必要に応じて存在しないフォルダーを作成してください。

|---------|---------------------------|
| ⟦L8:variables.product.prodname_copilot_short⟧ | ⟦I23⟧ または ⟦I24⟧ |
| ⟦L9:variables.product.prodname_anthropic_claude⟧ | ⟦I25⟧ |
| ⟦L10:variables.product.prodname_openai_codex⟧ | ⟦I26⟧ |
| ローカル ⟦I27⟧ | ⟦I28⟧ または ⟦I29⟧ |

ルールを追加してファイルを保存し、後述の手順に従って検証します。⟦I30⟧ は Codex 専用のファイルではなく、クロスエージェント形式です。1つのファイルを複数のハーネス間で共有する前に、[サポートされている形式](⟦U79⟧)を確認してください。

### 指示の検証

ルールが結果に影響を与える小さなタスクをテストします。最初から最後まで同じハーネスとリポジトリを使用してください。

1. コマンドパレット（⟦I31⟧）から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルが一覧表示されていることを確認します。これは、エージェントがルールに従っているかどうかではなく、ファイルの検出を確認するものです。
1. 指示を作成した会話からのガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプト内でルールを繰り返さずに、小さな変更を要求します。API の例では、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 利用可能な場合は、レスポンスの **References** セクションで指示ファイルを確認します。詳細が必要な場合は、[Agent デバッグログでリクエストを検査します](⟦U80⟧)。
1. 変更内容とツールの動作を確認します。例の場合、ハンドラーが追加された場所、データのアクセス方法、エージェントが関連するテストを実行したかどうかを確認します。

結果が目標を満たしている場合は、チームが使用できるように指示ファイルをレビューしてコミットします。満たしていない場合は、ルールを追加する前に、[ファイルが検出されたか、含まれていたか、従われたかを確認します](⟦U81⟧)。

完全な比較（変更前と変更後）およびチームへの展開ワークフローについては、[コードベースの AI の構成](⟦U82⟧)に従ってください。

## 指示の適用方法

スコープとアクティベーション（有効化）は、異なる疑問に答えるものです。スコープは、ガイダンスがどこで使用可能であり、誰がそれを共有するかを決定します。アクティベーションは、そのガイダンスがリクエストにいつ含まれるかを決定します。

| スコープ | 使用目的 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有されるプロジェクトの規則 |
| ユーザー | ハーネスでサポートされている場所における、プロジェクトをまたいだ個人的な設定 |
| 組織 | サポートされているエクスペリエンス向けに一元管理されたガイダンス |

幅広く適用されるルールには、プロジェクト指示を使用します。コードベースの一部のみで必要なガイダンスには、ターゲットを絞った指示を使用します。

| アクティベーション | 仕組み |
|------------|--------------|
| プロジェクト全体 | ハーネスはプロジェクト指示ファイルからのガイダンスを含めます。 |
| ファイルパターン | ⟦I32⟧ ファイルは ⟦I33⟧ を使用するか、Claude ルールファイルは ⟦I34⟧ を使用して、エージェントが処理するファイルに一致させます。 |
| タスクの関連性 | ローカルセッションでは、⟦I35⟧ により、エージェントがタスクの指示ファイルを読み取るかどうかを決定できます。これはパターンマッチングとは別に行われます。 |
| 手動 | 自動検出またはアクティベーションが適切ではない特定のリクエストにガイダンスを添付します。 |

⟦I36⟧ などの指示ファイルは、既存のエージェントにガイダンスを提供します。[カスタムエージェント](⟦U83⟧)を定義するものではありません。コーディング規則やプロジェクトコンテキストではなく、再利用可能なマルチステップのワークフローが必要な場合は、[エージェントスキル](⟦U84⟧)の検討をお勧めします。ワークフローを自分で作成する前に、[カスタマイズマーケットプレイスで既存のスキルを探してください](⟦U85⟧)。リポジトリ固有のコマンドと規則は、プロジェクト指示に記述してください。

### 1つのリクエストへの指示の添付

1回限りの要件については、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

1つのリクエストで既存の指示ファイルを再利用するには、チャット入力欄の **Add Context**（⟦I68⟧ アイコン）を選択し、リクエストを送信する前にファイルを選択します。

## 効果的な指示の作成

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを作成します。

| 次のようにする代わりに | 次のように書く |
|------------|-------|
| 良いテストを書く。 | ⟦I69⟧ からフィクスチャを再利用し、テストを変更した後に ⟦I70⟧ を実行する。 |
| アーキテクチャに従う。 | HTTP ハンドラーが独立してテスト可能な状態を維持できるように、データベースアクセスを ⟦I71⟧ 内に維持する。 |
| スタイルに従う。 | エラー文字列を返すのではなく、⟦I72⟧ の既存のエラータイプを使用する。 |

* **ルールを簡潔に保つ。** 各要件に対して短い文を使用し、自明ではない制約事項を説明します。
* **実行可能な詳細を優先する。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避ける。** フォーマッターやリンターによって強制されるルールを重複させないでください。プロジェクト全体のファイルから専門的なガイダンスを移動します。
* **コードと一緒に指示を維持する。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを慎重に参照する。** 相対パスと ⟦I73⟧ 区切り文字を使用した Markdown リンクを使用します。リンクによってドキュメントの内容がモデルに確実に届くとは限りません。[参照ファイルの動作](⟦U88⟧)を確認してください。

### 競合する指示の解決

個人、リポジトリ、組織のガイダンスの間で、共有される要件の一貫性を保ちます。普遍的な優先順位の順序に依存しないでください。[組み合わせルールはハーネスによって異なります](⟦U89⟧)。

個人の指示で1つのライブラリが要求され、リポジトリで別のライブラリが必要とされる場合は、競合する個人のルールを削除するか絞り込みます。補正するためにもう1つのルールを追加しないでください。競合を解決した後に、同じ代表的なタスクを新しいチャットで繰り返します。

## プロジェクト指示と個人指示の管理

Agent Customizations エディターの **Instructions** に戻って、既存の指示を見つけて編集します。個人指示を追加するには、**User** の横にある ⟦I74⟧ を選択します。ハーネスでサポートされている名前と保存先のプロンプトに従い、ファイルを保存して、そのハーネスを使用した新しいチャットで検証します。

プロジェクトをまたいだ個人的な設定には、ユーザー用のスコープを使用します。チームが求めている場合を除き、個人の応答の好みを共有プロジェクトファイルに入れないでください。場所と同期の制限については、[ユーザー指示](⟦U90⟧)を参照してください。

関連するエージェント、スキル、またはツールとともに、[エージェントプラグイン](⟦U91⟧)内のルールコンポーネントとして指示を配布することもできます。サポートは、選択したハーネスとプラグインの形式によって異なります。バンドルをクライアント間で共有する前に、[プラグインの互換性](⟦U92⟧)を確認してください。

## 指示のトラブルシューティング

ガイダンスを変更する前に、障害の発生ステージを特定します。

| 観測される現象 | 確認すべきこと |
|------------------|---------------|
| カスタマイズエディターにファイルが一覧表示されない。 | 選択されているハーネス、ファイル名、サポートされている場所、およびセッションが変更を含むフォルダーを使用しているかどうかを確認します。 |
| ファイルが検出されたが、タスクに含まれていない。 | フロントマターのエラーとアクティベーション条件を確認します。一致するファイルをテストするか、手動で指示を添付します。ローカルの場合は、適用可能な[検出設定](⟦U99⟧)を確認してください。 |
| ファイルが含まれているが、結果がそれに従っていない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返して、実際の変更点とツールの動作を比較します。 |

利用可能な場合のレスポンスの **References** セクションは、準拠ではなく包含を確認するのに役立ちます。詳細な証拠については、[指示の診断](⟦U100⟧)に従ってください。問題を再現する前にロギングを準備してください。
