# 翻訳モデルの選び方（案）

一次訳に使うモデルを選ぶための、訳し比べの手順と評価の仕方の案です。どの方針を採るかも、どのモデルを一次訳に使うかも、ここでは決めません。翻訳本文の作成と、パイプラインの実装は、この文書の対象外です。

この文書の作成日は2026年11月11日（Asia/Tokyo）です。費用の数字は、同日時点の[翻訳方法の比較と推奨](translation-method.md)の見積もりを使います。訳し方の規則は、[訳し方の指針と用語集（案）](translation-guidelines.md)の決定事項に従います。

## この資料の位置づけ

[翻訳方法の比較と推奨](translation-method.md)には、料金の比較と、モデル選定の大まかな進め方が既にあります。こちらは、その「訳し比べ」を、同じページ、同じ観点、同じ採点表で行うための手順です。

主題は、英語を自然で正確な日本語にできているかどうかです。マークダウンやLiquidが壊れていないかは、別欄で記録します。書式の保全は、訳質の採点には使いません。

DeepLなどの機械翻訳APIと、いわゆる強いモデルを使わない案は、検討中です。決定ではありません。ここでいう強いモデルとは、GPT-6.1 Sol、Claude Sonnet 5.5、Gemini 4 Argon、Claude Opus 5.5、GPT-6 Astraを指します。詳しくは、翻訳方法の文書の[DeepLと強いモデルを使わない案（検討中）](translation-method.md#deeplと強いモデルを使わない案検討中)を参照してください。

## 比べる対象

候補の範囲は、採用する方針によって変わります。どちらを採るかは未決です。

**安価なモデルとPLaMoに限る場合**の候補は、次のとおりです。

- GPT-6 Luna（Batch）
- Claude Haiku 5.5（Batch）
- Gemini 3.5 Flash-Lite（Batch）
- DeepSeek Flash（オフピーク）
- Gemini 3.8 Flash（Batch。2026年内の価格）
- PLaMo 3.1 Prime（API Standard）
- PLaMo 3 Translate（ローカル、またはレンタルGPU）

PLaMo 3 Translateは、0.8B、2B、8B、31Bがあります。PFNの自社評価でGPT-6.1 Sol並みとされているのは31Bです。手元の環境に余裕があれば、8Bと31Bの両方を試す余地があります。試すサイズは、訳し比べの時点で決めます。

**品質の高いモデルも含める場合**は、上記に加えて、GPT-6.1 Sol、Claude Sonnet 5.5、Gemini 4 Argonなどを同じ標本で訳します。強いモデルを一次訳に使うかどうかは、その結果を見てからでも間に合います。

DeepL、Google翻訳、Azure Translatorは、どちらの案でも比較対象に入れない前提で書いています。方針が変われば、そのときに足します。

指示文、用語集、敬体の指定、プレースホルダの退避は、候補のあいだで揃えます。PLaMo 3 Translateだけ、用語集と常体・敬体の指定を専用欄で渡せる点が違います。渡す中身は、ほかのモデルの指示文と同じものにします。

## 固定する標本

初版の20ページをすべて訳しても、費用はほとんど問題になりません。ただし、人が読み比べるには多すぎます。ここでは、初版から6ページを固定の標本とします。一度決めたら、あとの追試でも同じ6ページを使います。モデルを足したときに、条件がずれないようにするためです。

選び方は、次の3点です。

- VS Codeのリリースノート、エージェント周辺の操作説明、GitHub Docsの解説と手順が、偏らず入ること
- 製品名やUIの文言、custom instructions、Agent modeなど、指針で決めた語が実際に出ること
- 公式日本語版で書式や訳文が崩れていたページを、少なくとも2つ含めること


| # | 系統 | 上流パス | 入れる理由 |
| ---: | --- | --- | --- |
| 1 | VS Code | `release-notes/v1_146.md` | 週次リリースの長い記事です。新しい機能名と、短い説明文が混在します |
| 6 | VS Code | `docs/agents/run/agents-window.md` | Agents windowなど、画面名を英語のまま残す操作説明です |
| 11 | VS Code | `docs/agent-customization/custom-instructions.md` | 機能名のcustom instructionsと、一般の「指示」の見分けが問われます |
| 13 | GitHub Docs | `content/copilot/concepts/agent-capabilities/about-agents/about-github-copilot-agents.md` | 概念の解説です。機能名と一般の「エージェント」が入り混じります |
| 14 | GitHub Docs | `content/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github.md` | 公式日本語版で語順や太字、手順リストが崩れていた、Webからの主How-toです |
| 18 | GitHub Docs | `content/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment.md` | 公式日本語版で表やコード、`AUTOTITLE`が崩れていた設定ページです |

番号は、[サイト構成案](site-structure.md#初版スコープ)の初版20ページと同じです。原文のコミットも、同文書の調査時点（`microsoft/vscode-docs@0cc882e`、`github/docs@7c3387d`）に揃えます。あとから上流が動いても、この訳し比べでは同じコミットを使います。

人が通読するのは、原則としてこの6ページです。リントは、訳した範囲の全セグメントにかけます。初版20ページをすべて機械訳して合格率だけ見るのは、費用の余裕があれば足してかまいません。その場合も、人が読む標本はこの6ページのままにします。

これらのページが参照する`data/reusables`や`data/variables`は、本文と同じ条件で訳し、本文と一緒に渡します。文だけ、あるいは段落だけを切って訳すと、ページ内の略語や定義が別の意味に置き換わることがあるためです。

## 評価の観点

観点は、指針で決まった11点と、訳文としての正確さ・自然さに分けます。書式の保全は、参考記録です。

### 人が見る観点（本質）

正確さと自然さは、プログラムでは判定できません。次を人が読みます。

| 観点 | 見るところ | 根拠 |
| --- | --- | --- |
| 正確さ | 原文の意味が保てているか。事実の取り違え、訳抜け、勝手な短縮や補足が無いか | 翻訳の主題そのものです |
| 自然さ | 初めから日本語で書かれたように読めるか。不要な人称、受身の濫用、「〜することができます」などの翻訳調が残っていないか | 指針の「翻訳調を避ける」 |
| 文脈に応じた用語 | 機能名・固有名詞は英語のまま、一般の意味の箇所だけ訳せているか。同じ語を、ページの途中で別の扱いにしていないか | 決定事項の9 |
| 手順の文末 | 手順は「〜します」、注意や必須の操作だけ「〜してください」になっているか | 決定事項の3 |

「文脈に応じた用語」と「手順の文末」は、リントでも粗い検出はできます。ただし、その文が機能名なのか一般の意味なのか、注意文なのか通常の手順なのかは、人が判断します。リントの指摘は手がかりであり、採点の対象にはしません。

### リントで見る観点（決定済みの表記）

次は、指針で既に決まっている表記です。機械で検出できるものは、機械に任せます。

| 観点 | 規則 | 根拠 |
| --- | --- | --- |
| 文体 | 本文は敬体（です・ます調）。見出しや表の項目、図のキャプションの体言止めは除く | 決定事項の1 |
| 製品名・UI | 英語のまま残し、原文の書式（太字の有無など）を保つ。訳の側で角括弧や太字を足さない | 決定事項の2、5 |
| pull requestとissue | 概念としても英語のまま。「プルリクエスト」「イシュー」「課題」などにはしない | 決定事項の6 |
| 和欧の空白 | 日本語と英数字のあいだに空白を入れない。リンクの閉じ括弧のあとや、#123のあとは除いてよい | 決定事項の7 |
| UI名への補足 | 英語のUI名に、日本語を括弧で補わない | 決定事項の8 |
| 数字と単位 | 詰めて書く。例: 10GB、3ms、80% | 決定事項の10 |
| カタカナ複合語 | 空白で区切らない。例: アクセストークン | 決定事項の11 |
| 長音 | Microsoftの日本語スタイルガイドに従う。サーバ、ユーザ、フォルダの形は使わない。例外表の語は例外に従う | 決定事項の4 |
| 用語集の禁止形 | 「レポジトリ」など、指針で禁じている形が出ないこと | 用語集 |

リント規則の案は、[リント規則（案）](lint-rules.md)に分けて書きました。採用する項目も、検出の厳しさも、未決です。

### 参考にする観点（書式）

Liquidタグ、見出し、リスト、表、コードブロック、リンク、画像パス、フロントマターの構造が、原文と一致しているかは、リントで記録します。壊れた訳は、正確さや自然さの点から外して扱います。書式の失敗が多いモデルは、運用上の欠点として別途記します。訳質の順位付けには使いません。

## リントで見られること、人が見ること

役割の分け方は、次のとおりです。リントの中身そのものは未決ですので、できることの見立てです。

**リントに任せられること**

- である調の残存、禁止しやすい表現（「〜することができます」「あなたは」「弊社」など）
- 日本語と英数字のあいだの空白、数字と単位のあいだの空白、カタカナ複合語の区切り空白
- UI名への日本語の補足、全角英数字、和文に混じったカンマやピリオド、em dash（—）
- 長音の揺れ、用語集の禁止訳語、原文に無い太字や角括弧
- 原文との構造の一致（Markdown、リンク、コードブロック、Liquid、フロントマター）
- 訳抜けの形跡（英語の文の残留、長さの比が想定から大きく外れること）

**人が読むこと**

- 意味が正確か、日本語として自然か
- 機能名と一般の意味の見分けが、その文で妥当か
- 手順と注意の文末が、趣旨に合っているか
- 略語や、ページ内で定義された語の扱いが、そのページで一貫しているか
- リントが拾えない誤訳、過剰な意訳、原文に無い説明の追加

リントの合格率が高くても、人が読んで不自然なら、そのモデルは一次訳に向きません。逆に、表記の違反が多くても、誤りが機械で直せる種類ばかりなら、運用で補える場合があります。両方を並べて見ます。

## 試し訳の費用

数字は、[翻訳方法の比較と推奨](translation-method.md#llmのapiで全量を1回訳す場合)の、初版20ページ（本文と再利用片を合わせ、入力約7.0万トークン）の見積もりです。6ページだけの実測は、まだ出していません。リリースノートは長いので、単純に20分の6とは限りません。上限の目安として、20ページ分を使います。6ページだけなら、これを下回ります。

| モデル | 初版20ページの目安 | 6ページの試し訳 |
| --- | ---: | --- |
| GPT-6 Luna（Batch） | $0.03 | これを下回る |
| Claude Haiku 5.5（Batch） | $0.04 | これを下回る |
| DeepSeek Flash（オフピーク） | $0.08 | これを下回る |
| Gemini 3.5 Flash-Lite（Batch） | $0.14 | これを下回る |
| PLaMo 3.1 Prime（API Standard） | $0.21 | これを下回る |
| Gemini 3.8 Flash（Batch、2026年内の価格） | $0.23 | これを下回る |
| PLaMo 3 Translate（ローカル） | 電気代、またはGPU代 | 初版規模なら手元で足りる見込み |

安価なモデルとPLaMo APIを、20ページ分まで全部足しても、APIの費用は$1に届きません。6ページの標本なら、さらに少なくて済みます。品質の高いモデルまで20ページですべて回しても、レビュー込みで$5前後の見込みです。費用の差は、モデルを選ぶ決め手にはなりにくいです。

PLaMo 3 Translateを使う場合は、コミュニティライセンスの表示（「PLaMoを翻訳その他の変換に利用した」旨）の要否が残ります。これは[翻訳方法の比較と推奨](translation-method.md#未決事項)の未決事項です。試し訳の段階でも、結果のメモには使用したモデル名を残します。

## 進め方

次の順を提案します。途中で方針が変わっても、標本と採点表は変えません。

1. 指示文、用語集、退避の仕方を固定する。指針の決定事項を、指示にそのまま書く。
2. 各候補で、固定した6ページ（と、それが参照する再利用片）を訳す。任意で、初版20ページ全体も機械的に訳してよい。
3. 訳文をリントにかけ、表記規則と書式の違反を集計する。書式が壊れたセグメントは、人が読む対象から外し、書式の欄にだけ記録する。
4. 残った訳を、人が同じ順で読む。公式日本語版で崩れていた#14と#18は、必ず通読する。
5. 下の採点表に記入し、正確さ、自然さ、表記の違反、運用の手間を並べて見る。
6. 一次訳のモデルと、リントに通らなかったときの切り替え先を、その結果を材料に選ぶ。選ぶこと自体は、この文書では行いません。

不合格のあとの処理は、方針によって違います。強いモデルを使わない案では、同じ範囲の別モデルへ回すか、人の確認待ちにします。品質の高いモデルを使う案では、上位モデルへ格上げする流れもあります。詳しくは翻訳方法の文書を参照してください。

## 採点表のひな形

候補ごとに1枚使います。人が見る4つの観点は、5段階で点を付けます。5がよい側です。表記と書式は、違反の件数と、人が見た印象を書きます。配点を足して総点にはしません。性格の違う指標を、一つの数字にしないためです。

```text
モデル:
日付:
原文コミット: microsoft/vscode-docs@0cc882e / github/docs@7c3387d
方針の範囲: 安価なモデルとPLaMoのみ / 品質の高いモデルも含む

--- 人が見る点（1は低い、5は高い）---
正確さ:  /5
  誤訳・訳抜けのメモ:
自然さ:  /5
  翻訳調や、読みにくさのメモ:
用語の見分け（機能名と一般の意味）:  /5
  迷った箇所:
手順の文末:  /5
  「してください」の過不足:

ページごとのメモ:
  #1 リリースノート:
  #6 Agents window:
  #11 custom instructions:
  #13 agentsの概要:
  #14 GitHub上のクラウドエージェント:
  #18 エージェント環境の構成:

--- リント（参考）---
表記規則の違反:  件
  内訳（敬体、空白、長音、禁止訳語、UIの書式など）:
書式の違反:  件
  内訳（Liquid、表、コード、リンク、フロントマターなど）:
セグメント合格率:  %

--- 総評 ---
一次訳の候補にするか:
切り替え先にするか:
特記（運用の手間、ライセンス表示、長文の切れ方など）:
```

同じ人が、同じ日に、候補を並べて読むのが望ましいです。先に読んだ訳の印象が、あとの訳に乗らないよう、ページ単位で候補を入れ替えて読む方法もあります。やり方は、実際に読むときに決めます。

## 未決事項

1. **モデルの方針。** 安価なモデルとPLaMoに限るか、品質の高いモデルも含めるか。
2. **一次訳のモデル。** 訳し比べの結果を見て選ぶ。
3. **PLaMoを使う場合のライセンス表示。**
4. **人のレビューの範囲。** 試し訳では6ページを通読します。本番で、全ページを人が読むのか、抜き取りにするのかは、別途決める必要があります。
5. **リントの中身。** どの規則を採用し、どこまでを合格の条件にするか。案は[リント規則（案）](lint-rules.md)にあります。
