# <x id="26SY"/> でカスタムインストラクションを使用する

カスタムインストラクションを使用すると、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供できます。このガイダンスをすべてのプロンプトで繰り返すのではなく、Markdownファイルに保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている1つの規約から始めます。[Agent Customizations エディター](<x id="DZYT"/>)でインストラクションを作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、および設定については、[カスタムインストラクションのリファレンス](<x id="4W6R"/>)を参照してください。

インストラクションはモデルをガイドします。これらは準拠を保証したり、テスト、コードレビュー、セキュリティ制御を置き換えたりするものではありません。入力時の[インラインサジェスト](<x id="T72T"/>)には適用されません。

## プロジェクトインストラクションの開始

リポジトリのルートを開き、使用する予定の[エージェントハーネスを選択します](<x id="J83T"/>)。ハーネスによって、どのインストラクションファイルが読み取られるかが決まります。たとえば、<x id="C9A7"/> セッションで Claude モデルを選択しても、Claude ハーネスに切り替わるわけではありません。

最初のセットアップでは、テストセッションからコミットされていないインストラクションにアクセスできるようにするため、新しいワークツリーではなく現在のフォルダーで作業します。

### プロジェクトインストラクションの作成

1. コマンドパレット（<x id="RSFE"/>）から **Chat: Open Customizations** を実行して Agent Customizations エディターを開き、**Instructions** タブを選択します。

1. プロジェクトインストラクションファイルを追加するには、**Workspace** の横にある <x id="46HS"/> を選択し、<x id="ZRER"/> や <x id="VEJX"/> など、お使いのハーネスで提案されたプロジェクトインストラクションファイルを選択します。エディターによって、ファイルがワークスペースに作成されるか、既存のファイルが開きます。

   すでにリポジトリにプロジェクトインストラクションファイルが存在する場合は、競合するコピーを作成するのではなく、そのファイルを開いてください。

1. 繰り返されている問題に対処する具体的なルールをいくつか追加します。たとえば、Node.jsのAPIプロジェクトでは次のインストラクションを使用できます。パスとテストコマンドをリポジトリで動作するものに置き換えてください。

   <x id="KSF7"/>

1. ファイルを保存します。これらのプロジェクトインストラクションファイルにはフロントマターは必要ありません。

#### ファイルを直接作成する

Agent Customizations エディター以外の場所でファイルを作成したい場合は、お使いのハーネスでサポートされているプロジェクトインストラクションファイルを使用してください。以下のパスはリポジトリのルートからの相対パスです。必要に応じて不足しているフォルダーを作成してください。

|---------|---------------------------|
| <x id="8QXZ"/> | <x id="D7ND"/> または <x id="CJ8M"/> |
| <x id="6NXY"/> | <x id="8XC6"/> |
| <x id="RENG"/> | <x id="H7XR"/> |
| Local <x id="8YPR"/> | <x id="7BGB"/> または <x id="N554"/> |

ルールを追加し、ファイルを保存して、以下に説明するように検証します。<x id="QKM3"/> はクロスエージェント形式であり、Codex 専用のファイルではありません。複数のハーネス間で1つのファイルを共有する前に、[サポートされている形式](<x id="4BRQ"/>)を確認してください。

### インストラクションの検証

ルールが結果に影響を与えるような小さなタスクをテストします。最初から最後まで同じハーネスとリポジトリを使用します。

1. コマンドパレット（<x id="CDNA"/>）から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これは検出の確認であり、エージェントがルールに従っているかどうかの確認ではありません。
1. インストラクションを作成した会話のガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプトでルールを繰り返さずに、小さな変更を依頼します。APIの例であれば、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 利用可能な場合は、レスポンスの **References** セクションでインストラクションファイルを確認します。詳細が必要な場合は、[Agent Debug Logs でリクエストを検査します](<x id="8NCC"/>)。
1. 変更内容とツールの動作を確認します。例の場合は、ハンドラーが追加された場所、データのアクセス方法、およびエージェントが関連するテストを実行したかどうかを確認します。

結果が目標を満たしている場合は、チームが使用できるようにインストラクションファイルをレビューしてコミットします。そうでない場合は、さらにルールを追加する前に、[ファイルが検出されたか、含まれていたか、従われたかを確認します](<x id="AS5G"/>)。

前後の完全な比較とチームへの展開ワークフローについては、[コードベース向けAIの設定](<x id="YR7C"/>)に従ってください。

## インストラクションの適用方法

スコープと有効化（アクティベーション）は異なる疑問に答えます。スコープは、ガイダンスがどこで利用可能か、誰がそれを共有するかを決定します。有効化は、そのガイダンスがいつリクエストに含まれるかを決定します。

| スコープ | 用途 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有されるプロジェクト規約 |
| ユーザー | ハーネスでサポートされている場所における、プロジェクトを横断した個人的な好み |
| 組織 | サポートされているエクスペリエンス向けの中央管理されたガイダンス |

幅広く適用されるルールについては、プロジェクトインストラクションから始めます。コードベースの一部のみで必要なガイダンスには、ターゲットを絞ったインストラクションを使用します。

| 有効化 | 動作の仕組み |
|------------|--------------|
| プロジェクト全体 | ハーネスには、プロジェクトインストラクションファイルからのガイダンスが含まれます。 |
| ファイルパターン | エージェントが作業するファイルに一致させるために、<x id="J8RC"/> ファイルは <x id="EP9N"/> を使用するか、Claude ルールファイルは <x id="B9WF"/> を使用します。 |
| タスクの関連性 | Local セッションでは、<x id="TJC6"/> により、タスクに対するインストラクションファイルを読み込むかどうかをエージェントが決定できます。これはパターンマッチングとは別個のものです。 |
| 手動 | 自動検出や有効化が適切でない特定のりクエストにガイダンスを添付します。 |

<x id="5Y43"/> などのインストラクションファイルは、既存のエージェントにガイダンスを提供します。これは[カスタムエージェント](<x id="MA5Q"/>)を定義するものではありません。コーディング規約やプロジェクトコンテキストではなく、再利用可能なマルチステップのワークフローが必要な場合は、[エージェントスキル](<x id="E4X7"/>)を検討してください。ワークフローを自分で作成する前に、[カスタマイズマーケットプレイスで既存のスキルを探してください](<x id="3RV4"/>)。リポジトリ固有のコマンドや規約は、プロジェクトインストラクションに保持してください。

### 1つのリクエストにインストラクションを添付する

1回限りの要件の場合は、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

既存のインストラクションファイルを1回のリクエストに再利用するには、チャット入力欄にある **Add Context**（<x id="ET8M"/> アイコン）を選択し、リクエストを送信する前にそのファイルを選択します。

## 効果的なインストラクションの記述

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを記述します。

| 記述方法の変更前 | 記述方法の変更後 |
|------------|-------|
| 良いテストを書いてください。 | <x id="2AGA"/> のフィクスチャを再利用し、テストを変更した後に <x id="7RQB"/> を実行してください。 |
| アーキテクチャに従ってください。 | HTTPハンドラーが独立してテスト可能な状態を維持できるように、データベースアクセスを <x id="GB4P"/> に保持してください。 |
| 当社のスタイルに従ってください。 | エラー文字列を返すのではなく、<x id="AY5Y"/> の既存のエラー型を使用してください。 |

* **ルールを簡潔に保つ:** 各要件に対して短い文を使用し、自明ではない制約については説明を加えます。
* **実行可能な詳細を優先する:** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避ける:** フォーマッターやリンターによって強制されるルールを重複させないでください。プロジェクト全体のファイルから特殊なガイダンスを移動させます。
* **コードと一緒にインストラクションを維持する:** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを慎重に参照する:** 相対パスと <x id="PKKK"/> セパレーターを使用した Markdown リンクを使用します。リンクが存在しても、ドキュメントの内容がモデルに確実に到達するわけではありません。[参照されたファイルの動作](<x id="JP57"/>)を確認してください。

### 競合するインストラクションの解決

個人、リポジトリ、組織のガイダンスの間で、共有要件が一貫していることを確認します。普遍的な優先順位の順序に頼らないでください。[組み合わせのルールはハーネスによって異なります](<x id="DCSM"/>)。

個人のインストラクションで1つのライブラリが要求され、リポジトリで別のライブラリが要求されている場合は、競合している個人のルールを削除するか絞り込みます。それを補うために別のルールを追加しないでください。競合を解決した後に、新しいチャットで同じ代表的なタスクを繰り返します。

## プロジェクトおよび個人のインストラクションの管理

Agent Customizations エディターの **Instructions** に戻り、既存のインストラクションを探して編集します。個人のインストラクションを追加するには、**User** の横にある <x id="RCEE"/> を選択します。お使いのハーネスでサポートされている名前と保存場所に関するプロンプトに従い、ファイルを保存して、そのハーネスを使用した新しいチャットで検証します。

プロジェクトを横断した個人的な好みには、ユーザーのスコープを使用します。チームが求めている場合を除き、個人のレスポンスの好みは共有プロジェクトファイルに記述しないでください。場所と同期の制限については、[ユーザーインストラクション](<x id="X2DE"/>)を参照してください。

また、関連するエージェント、スキル、またはツールとともに、[エージェントプラグイン](<x id="EB44"/>)内のルールコンポーネントとしてインストラクションを配布することもできます。サポートは、選択されたハーネスとプラグインの形式によって異なります。複数のクライアント間でバンドルを共有する前に、[プラグインの互換性](<x id="MWJS"/>)を確認してください。

## インストラクションのトラブルシューティング

ガイダンスを変更する前に、失敗の段階を特定します。

| 発生している現象 | 確認すべきこと |
|------------------|---------------|
| カスタマイズエディターにファイルがリストされない。 | 選択したハーネス、ファイル名、サポートされている場所、およびセッションで変更を含むフォルダーが使用されているかどうかを確認します。 |
| ファイルが検出されているが、タスクに含まれていない。 | フロントマターのエラーと有効化の条件を確認します。一致するファイルをテストするか、手動でインストラクションを添付します。Local の場合は、該当する[検出設定](<x id="Y3BW"/>)を確認します。 |
| ファイルが含まれているが、結果がそれに従っていない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返して、実際の変更とツールの動作を比較します。 |

利用可能な場合、レスポンスの **References** セクションは、準拠ではなく包含（インクルージョン）の確認に役立ちます。詳細な証拠については、[インストラクションの診断](<x id="SJC8"/>)に従ってください。問題を再現する前にロギングを準備します。
