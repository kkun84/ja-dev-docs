# ⟦L6:variables.product.prodname_vscode_shortname⟧ でのカスタム指示の使用

カスタム指示を使用すると、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供できます。すべてのプロンプトで同じ内容を繰り返す代わりに、このガイダンスをMarkdownファイルに保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている1つの規約から始めます。[Agent Customizations エディター](⟦U75⟧)で指示を作成し、さらにターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、設定については、[カスタム指示リファレンス](⟦U76⟧)を参照してください。

指示はモデルをガイドするものです。準拠を保証したり、テスト、コードレビュー、セキュリティ制御の代わりになったりするものではありません。[インラインサジェスト](⟦U77⟧)を入力時には適用されません。

## プロジェクト指示の開始

リポジトリのルートを開き、使用する予定の[エージェントハーネスを選択します](⟦U78⟧)。ハーネスによって、どの指示ファイルが読み込まれるかが決まります。たとえば、⟦L7:variables.product.prodname_copilot_short⟧ セッションで Claude モデルを選択しても、Claude ハーネスには切り替わりません。

最初のセットアップでは、テストセッションからコミットされていない指示にアクセスできるようにするため、新しいワークツリーではなく現在のフォルダーで作業します。

### プロジェクト指示の作成

1. コマンドパレット (⟦I19⟧) から **Chat: Open Customizations** を実行して Agent Customizations エディターを開き、**Instructions** タブを選択します。

1. プロジェクト指示ファイルを追加するには、**Workspace** の横にある ⟦I20⟧ を選択し、⟦I21⟧ や ⟦I22⟧ など、ハーネスに合わせて提供されるプロジェクト指示ファイルを選択します。エディターはワークスペース内にファイルを作成または開きます。

   リポジトリにすでにプロジェクト指示ファイルが存在する場合は、競合するコピーを作成せずにそのファイルを開いてください。

1. 繰り返されている問題に対処するいくつかの具体的なルールを追加します。たとえば、Node.js の API プロジェクトでは、次の指示を使用できます。パスとテストコマンドを、リポジトリで機能するものに置き換えてください。

   ⟦C1⟧

1. ファイルを保存します。これらのプロジェクト指示ファイルにはフロントマターは必要ありません。

| ⟦L9:variables.product.prodname_anthropic_claude⟧ | ⟦I25⟧ |
| ⟦L10:variables.product.prodname_openai_codex⟧ | ⟦I26⟧ |
| ローカル ⟦I27⟧ | ⟦I28⟧ または ⟦I29⟧ |

ルールを追加してファイルを保存し、以下で説明するように検証します。⟦I30⟧ はクロスエージェントのフォーマットであり、Codex 専用のファイルではありません。1つのファイルを複数のハーネス間で共有する前に、[サポートされているフォーマット](⟦U79⟧)を参照してください。

### 指示の検証

ルールが結果に影響を与える小さなタスクをテストします。最初から最後まで同じハーネスとリポジトリを使用します。

1. コマンドパレット (⟦I31⟧) から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これは、エージェントがルールに従うかどうかではなく、ファイルの検出を確認するものです。
1. 指示を作成した会話のガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプトでルールを繰り返さずに、小さな変更を依頼します。API の例では、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 可能であれば、応答の **References** セクションで指示ファイルを確認します。さらに詳細が必要な場合は、[Agent デバッグログでリクエストを検査します](⟦U80⟧)。
1. 変更内容とツールの動作を確認します。例の場合は、ハンドラーが追加された場所、データのアクセス方法、エージェントが関連するテストを実行したかどうかを確認します。

結果が目標を満たしている場合は、チームが使用できるように指示ファイルをレビューしてコミットします。満たしていない場合は、さらにルールを追加する前に、[ファイルが検出されたか、含まれていたか、従われたかを確認します](⟦U81⟧)。

完全な変更前後の比較とチームへのロールアウトワークフローについては、[コードベース向けに AI を構成する](⟦U82⟧)に従ってください。

## 指示の適用方法

スコープとアクティベーションは異なる質問に答えます。スコープは、ガイダンスがどこで使用可能か、誰がそれを共有するかを決定します。アクティベーションは、そのガイダンスがいつリクエストに含まれるかを決定します。

| スコープ | 用途 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有されるプロジェクト規約 |
| ユーザー | ハーネスでサポートされている場所における、プロジェクトをまたいだ個人の好み |
| 組織 | サポートされているエクスペリエンス向けに一元管理されたガイダンス |

幅広く適用されるルールにはプロジェクト指示から始めます。コードベースの一部のみで必要なガイダンスには、ターゲットを絞った指示を使用します。

| アクティベーション | 仕組み |
|------------|--------------|
| プロジェクト全体 | ハーネスはプロジェクト指示ファイルからのガイダンスを含めます。 |
| ファイルパターン | ⟦I32⟧ ファイルは ⟦I33⟧ を使用するか、Claude ルールファイルは ⟦I34⟧ を使用して、エージェントが処理するファイルに一致させます。 |
| タスクの関連性 | ローカルセッションでは、⟦I35⟧ により、エージェントがタスクの指示ファイルを読み込むかどうかを決定できます。これはパターンマッチングとは別です。 |
| 手動 | 自動検出やアクティベーションが適切ではない特定のリクエストにガイダンスを添付します。 |

⟦I36⟧ などの指示ファイルは、既存のエージェントにガイダンスを提供します。[カスタムエージェント](⟦U83⟧)を定義するものではありません。コーディング規約やプロジェクトコンテキストではなく、再利用可能なマルチステップのワークフローが必要な場合は、[エージェントスキル](⟦U84⟧)を検討してください。自分でワークフローを作成する前に、[カスタマイズマーケットプレイスで既存のスキルを探してください](⟦U85⟧)。リポジトリ固有のコマンドと規約はプロジェクト指示に保持してください。

### 1つのリクエストに指示を添付する

1回限りの要件については、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

1つのリクエストで既存の指示ファイルを再利用するには、チャット入力の **Add Context** (⟦I68⟧ アイコン) を選択し、リクエストを送信する前にファイルを選択します。

## 効果的な指示の記述

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを記述します。

| 代わりに | 次のように記述 |
|------------|-------|
| 良いテストを書いてください。 | ⟦I69⟧ からフィクスチャを再利用し、テストを変更した後に ⟦I70⟧ を実行します。 |
| アーキテクチャに従ってください。 | HTTP ハンドラーが個別にテスト可能な状態を維持できるように、データベースアクセスを ⟦I71⟧ に保持します。 |
| スタイルに従ってください。 | エラー文字列を返すのではなく、⟦I72⟧ の既存のエラータイプを使用します。 |

* **ルールを簡潔に保ちます。** 各要件に対して短い文を使用し、自明ではない制約については説明します。
* **実行可能な詳細を優先します。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避けます。** フォーマッターやリンターによって強制されるルールを重複させないでください。プロジェクト全体のファイルから専門的なガイダンスを移動します。
* **コードと一緒に指示を維持します。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを注意して参照します。** 相対パスと ⟦I73⟧ 区切り文字を使用した Markdown リンクを使用します。リンクは、ドキュメントの内容がモデルに届くことを保証するものではありません。[参照ファイルの動作](⟦U88⟧)を確認してください。

### 競合する指示の解決

個人、リポジトリ、組織のガイダンス間で共有要件を一貫させます。普遍的な優先順位順に依存しないでください。[組み合わせのルールはハーネスによって異なります](⟦U89⟧)。

個人の指示で1つのライブラリが要求され、リポジトリで別のライブラリが必要とされる場合は、競合する個人のルールを削除するか絞り込みます。補正するためにもう1つのルールを追加しないでください。競合を解決した後に、新しいチャットで同じ代表的なタスクを繰り返します。

## プロジェクトおよび個人の指示の管理

Agent Customizations エディターの **Instructions** に戻って、既存の指示を見つけて編集します。個人用の指示を追加するには、**User** の横にある ⟦I74⟧ を選択します。ハーネスでサポートされている名前と保存場所のプロンプトに従い、ファイルを保存し、そのハーネスを使用した新しいチャットで検証します。

プロジェクトをまたいだ個人の好みには、ユーザースコープを使用します。チームが望んでいない限り、個人の応答の好みを共有プロジェクトファイルに入れないでください。場所と同期の制限については、[ユーザー指示](⟦U90⟧)を参照してください。

また、関連するエージェント、スキル、またはツールとともに、[エージェントプラグイン](⟦U91⟧)内のルールコンポーネントとして指示を配布することもできます。サポートは、選択したハーネスとプラグインフォーマットによって異なります。バンドルをクライアント間で共有する前に、[プラグインの互換性](⟦U92⟧)を確認してください。

## 指示のトラブルシューティング

ガイダンスを変更する前に、失敗のステージを特定します。

| 観察される内容 | 確認すべきこと |
|------------------|---------------|
| カスタマイズエディターにファイルがリストされていない。 | 選択したハーネス、ファイル名、サポートされている場所、およびセッションに変更を含むフォルダーを使用しているかどうかを確認します。 |
| ファイルは検出されたが、タスクに含まれていない。 | フロントマターのエラーとアクティベーション条件を確認します。一致するファイルをテストするか、手動で指示を添付します。ローカルの場合は、該当する[検出設定](⟦U99⟧)を確認します。 |
| ファイルは含まれているが、結果がそれに従っていない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返し、実際の変更点とツールの動作を比較します。 |

可能であれば、応答の **References** セクションは、コンプライアンスではなく、取り込みを確認するのに役立ちます。詳細な証拠については、[指示の診断](⟦U100⟧)に従ってください。問題を再現する前にロギングを準備します。
