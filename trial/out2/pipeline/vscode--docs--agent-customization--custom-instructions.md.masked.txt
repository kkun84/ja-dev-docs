# ⟦L6:variables.product.prodname_vscode_shortname⟧ でのカスタム指示の使用

カスタム指示を使用すると、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供できます。このガイダンスをすべてのプロンプトで繰り返すのではなく、Markdownファイルに保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている1つの規約から始めます。[Agent Customizationsエディター](⟦U75⟧)で指示を作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、および設定については、[カスタム指示リファレンス](⟦U76⟧)を参照してください。

指示はモデルをガイドするものです。コンプライアンスを保証するものではなく、テスト、コードレビュー、セキュリティ制御の代わりにもなりません。入力時の[インラインサジェスチョン](⟦U77⟧)には適用されません。

## プロジェクト指示の概要

リポジトリのルートを開き、使用する予定の[エージェントハーネスを選択します](⟦U78⟧)。どの指示ファイルを読み取るかは、ハーネスによって決まります。たとえば、⟦L7:variables.product.prodname_copilot_short⟧セッションでClaudeモデルを選択しても、Claudeハーネスには切り替わりません。

最初のセットアップでは、テストセッションからコミットされていない指示にアクセスできるようにするため、新しいワークツリーではなく現在のフォルダーで作業します。

### プロジェクト指示の作成

1. コマンドパレット（⟦I19⟧）から **Chat: Open Customizations** を実行してAgent Customizationsエディターを開き、**Instructions** タブを選択します。

1. プロジェクト指示ファイルを追加するには、**Workspace** の横にある ⟦I20⟧ を選択し、⟦I21⟧ や ⟦I22⟧ など、ハーネス用に提示されたプロジェクト指示ファイルを選択します。エディターによってワークスペース内にファイルが作成またはオープンされます。

   リポジトリにすでにプロジェクト指示ファイルが存在する場合は、競合するコピーを作成するのではなく、既存のファイルを開いてください。

1. 繰り返される問題に対処するいくつかの具体的なルールを追加します。たとえば、Node.jsのAPIプロジェクトでは、次の指示を使用する場合があります。パスとテストコマンドを、リポジトリで機能するものに置き換えてください。

   ⟦C1⟧

1. ファイルを保存します。これらのプロジェクト指示ファイルにフロントマターは必要ありません。

Agent Customizationsエディター以外でファイルを作成したい場合は、ハーネスでサポートされているプロジェクト指示ファイルを使用します。以下のパスはリポジトリのルートからの相対パスです。必要に応じて存在しないフォルダーを作成してください。

| ⟦L9:variables.product.prodname_anthropic_claude⟧ | ⟦I25⟧ |
| ⟦L10:variables.product.prodname_openai_codex⟧ | ⟦I26⟧ |
| ローカル ⟦I27⟧ | ⟦I28⟧ または ⟦I29⟧ |

ルールを追加してファイルを保存し、以下で説明するように検証します。⟦I30⟧ はクロスエージェントのフォーマットであり、Codex専用のファイルではありません。1つのファイルを複数のハーネス間で共有する前に、[サポートされているフォーマット](⟦U79⟧)を参照してください。

### 指示の検証

ルールが結果に影響を与える小さなタスクをテストします。最初から最後まで同じハーネスとリポジトリを使用します。

1. コマンドパレット（⟦I31⟧）から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これは発見の確認であり、エージェントがルールに従っているかどうかの確認ではありません。
1. 指示を作成した会話のガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプトでルールを繰り返さずに、小さな変更を依頼します。APIの例であれば、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 利用可能な場合は、レスポンスの **References** セクションで指示ファイルを確認します。詳細が必要な場合は、[Agent Debug Logsでリクエストを検査します](⟦U80⟧)。
1. 変更内容とツールの動作を確認します。例の場合は、ハンドラーが追加された場所、データのアクセス方法、およびエージェントが関連するテストを実行したかどうかを確認します。

結果が目標を満たしている場合は、チームが使用できるように指示ファイルをレビューしてコミットします。満たしていない場合は、ルールを追加する前に、[ファイルが発見されたか、含まれていたか、従われたかを確認します](⟦U81⟧)。

完全な変更前後の比較とチームへの展開ワークフローについては、[コードベース向けAIの設定](⟦U82⟧)に従ってください。

## 指示の適用方法

スコープとアクティベーションは異なる質問に答えるものです。スコープによって、ガイダンスを利用できる場所とそれを共有するユーザーが決まります。アクティベーションによって、そのガイダンスがリクエストにいつ含まれるかが決まります。

| スコープ | 用途 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有されるプロジェクト規約 |
| ユーザー | ハーネスでサポートされている場所における、プロジェクトをまたいだ個人的な設定 |
| 組織 | サポートされているエクスペリエンス向けの一元管理されたガイダンス |

幅広く適用されるルールには、プロジェクト指示から始めます。コードベースの一部のみで必要なガイダンスには、ターゲットを絞った指示を使用します。

| アクティベーション | 動作の仕組み |
|------------|--------------|
| プロジェクト全体 | ハーネスには、そのプロジェクト指示ファイルからのガイダンスが含まれます。 |
| ファイルパターン | ⟦I32⟧ ファイルでは ⟦I33⟧ を使用するか、Claudeルールファイルでは ⟦I34⟧ を使用して、エージェントが操作するファイルに一致させます。 |
| タスクの関連性 | ローカルセッションでは、⟦I35⟧ により、エージェントがタスクの指示ファイルを読み取るかどうかを決定できます。これはパターンマッチングとは別です。 |
| 手動 | 自動的な発見やアクティベーションが適切ではない特定のリクエストに対して、ガイダンスを添付します。 |

⟦I36⟧ などの指示ファイルは、既存のエージェントにガイダンスを提供します。[カスタムエージェント](⟦U83⟧)を定義するものではありません。コーディング規約やプロジェクトコンテキストではなく、再利用可能な複数ステップのワークフローの場合は、[エージェントスキル](⟦U84⟧)を検討してください。自分でワークフローを作成する前に、[カスタマイズマーケットプレイスで既存のスキルを探します](⟦U85⟧)。リポジトリ固有のコマンドと規約は、プロジェクト指示に記述してください。

### 1つのリクエストに指示を添付する

1回限りの要件については、共有ルールを作成する代わりに、プロンプトにガイダンスを記述します。

1つのリクエストのために既存の指示ファイルを再利用するには、チャット入力欄にある **Add Context**（⟦I68⟧ アイコン）を選択し、リクエストを送信する前にファイルを選択します。

## 効果的な指示の記述

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下しやすくなるルールを記述します。

| ❌ 避けるべき記述 | ⭕ 推奨される記述 |
|------------|-------|
| 良いテストを書く。 | ⟦I69⟧ からフィクスチャを再利用し、テストを変更した後に ⟦I70⟧ を実行する。 |
| アーキテクチャに従う。 | HTTPハンドラーが独立してテスト可能な状態を維持できるように、データベースアクセスは ⟦I71⟧ に留める。 |
| スタイルに従う。 | エラー文字列を返すのではなく、⟦I72⟧ 内の既存のエラー型を使用する。 |

* **ルールを簡潔に保つ。** 各要件に対して短い文を使用し、自明ではない制約について説明します。
* **実行可能な詳細を優先する。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避ける。** フォーマッターやリンターによって強制されるルールを重複させないでください。プロジェクト全体の設定ファイルから特殊なガイダンスを移動させます。
* **コードとともに指示を維持する。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを慎重に参照する。** 相対パスと ⟦I73⟧ 区切り文字を使用したMarkdownリンクを使用します。リンクがあるからといって、ドキュメントの内容がモデルに届くことが保証されるわけではありません。[参照されたファイルの動作](⟦U88⟧)を確認してください。

### 矛盾する指示の解決

共有要件は、個人的な設定、リポジトリ、組織のガイダンス間で一貫性を保ちます。普遍的な優先順位の順序に依存しないでください：[組み合わせのルールはハーネスによって異なります](⟦U89⟧)。

個人の指示で1つのライブラリが要求され、リポジトリで別のライブラリが必要とされる場合は、矛盾する個人的なルールを削除するか絞り込みます。補うための別のルールを追加しないでください。競合を解決した後、新しいチャットで同じ代表的なタスクを繰り返します。

## プロジェクト指示と個人指示の管理

既存の指示を見つけて編集するには、Agent Customizationsエディターの **Instructions** に戻ります。個人指示を追加するには、**User** の横にある ⟦I74⟧ を選択します。ハーネスでサポートされている名前と保存場所のプロンプトに従い、ファイルを保存し、そのハーネスを使用した新しいチャットで検証します。

プロジェクトをまたいだ個人的な設定には、ユーザースコープを使用します。チームも望んでいない限り、個人のレスポンス設定を共有のプロジェクトファイルに入れないでください。場所と同期の制限については、[個人指示](⟦U90⟧)を参照してください。

関連するエージェント、スキル、ツールとともに、[エージェントプラグイン](⟦U91⟧)内のルールコンポーネントとして指示を配布することもできます。サポートは、選択されたハーネスとプラグインのフォーマットによって異なります。クライアント間でバンドルを共有する前に、[プラグインの互換性](⟦U92⟧)を確認してください。

## 指示のトラブルシューティング

ガイダンスを変更する前に、失敗の段階を特定します。

| 発生している現象 | 確認すべきこと |
|------------------|---------------|
| ファイルがCustomizationsエディターに表示されない。 | 選択されたハーネス、ファイル名、サポートされている場所、およびセッションが変更内容を含むフォルダーを使用しているかどうかを確認します。 |
| ファイルが発見されているが、タスクに含まれていない。 | フロントマターのエラーとアクティベーション条件を確認します。一致するファイルをテストするか、指示を手動で添付します。ローカルの場合は、該当する[発見設定](⟦U99⟧)を確認します。 |
| ファイルが含まれているが、結果がそれに従っていない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返し、実際の変更とツールの動作を比較します。 |

利用可能な場合、レスポンスの **References** セクションは、コンプライアンスではなく包含の確認に役立ちます。詳細な証拠については、[指示の診断](⟦U100⟧)に従ってください。問題の再現前にロギングを準備してください。
