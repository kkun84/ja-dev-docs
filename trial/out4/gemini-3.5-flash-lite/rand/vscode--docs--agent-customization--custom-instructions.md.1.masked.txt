# ⟦26SY⟧ でカスタムインストラクションを使用する

カスタムインストラクションは、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供します。このガイダンスをすべてのプロンプトで繰り返すのではなく、Markdown ファイルに保存し、ソース管理を通じてプロジェクトのインストラクションを共有します。

エージェントが繰り返し見落としている1つの規約から始めます。[Agent Customizations エディター](⟦DZYT⟧)でインストラクションを作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、および設定については、[カスタムインストラクションのリファレンス](⟦4W6R⟧)を参照してください。

インストラクションはモデルをガイドします。これらは、コンプライアンスを保証するものではなく、テスト、コードレビュー、またはセキュリティ制御の代わりになるものでもありません。入力時の[インラインサジェスチョン](⟦T72T⟧)には適用されません。

## プロジェクトインストラクションの開始

リポジトリのルートを開き、使用する予定の[エージェントハーネスを選択](⟦J83T⟧)します。ハーネスによって、読み取るインストラクションファイルが決まります。たとえば、⟦C9A7⟧ セッションで Claude モデルを選択しても、Claude ハーネスには切り替わりません。

最初のセットアップでは、テストセッションからコミットされていないインストラクションにアクセスできるように、新しいワークツリーではなく現在のフォルダーで作業します。

### プロジェクトインストラクションの作成

1. コマンドパレット (⟦RSFE⟧) から **Chat: Open Customizations** を実行して Agent Customizations エディターを開き、**Instructions** タブを選択します。

1. プロジェクトインストラクションファイルを追加するには、**Workspace** の横にある ⟦46HS⟧ を選択し、⟦ZRER⟧ や ⟦VEJX⟧ など、ハーネスに対して提供されているプロジェクトインストラクションファイルを選択します。エディターはワークスペース内でファイルを作成または開きます。

   リポジトリにすでにプロジェクトインストラクションファイルがある場合は、競合するコピーを作成するのではなく、それを開きます。

1. 繰り返される問題に対処するいくつかの具体的なルールを追加します。たとえば、Node.js の API プロジェクトでは次のインストラクションを使用できます。パスとテストコマンドを、リポジトリで機能するものに置き換えてください。

   ⟦KSF7⟧

1. ファイルを保存します。これらのプロジェクトインストラクションファイルにはフロントマターは必要ありません。

#### ファイルを直接作成する

Agent Customizations エディター以外の場所でファイルを作成したい場合は、ハーネスでサポートされているプロジェクトインストラクションファイルを使用してください。以下のパスはリポジトリのルートからの相対パスです。必要に応じて、存在しないフォルダーを作成してください。

| ハーネス | プロジェクトインストラクションファイル |
|---------|---------------------------|
| ⟦8QXZ⟧ | ⟦D7ND⟧ または ⟦CJ8M⟧ |
| ⟦6NXY⟧ | ⟦8XC6⟧ |
| ⟦RENG⟧ | ⟦H7XR⟧ |
| ローカル ⟦8YPR⟧ | ⟦7BGB⟧ または ⟦N554⟧ |

ルールを追加し、ファイルを保存し、以下で説明するように検証します。⟦QKM3⟧ は Codex 専用のファイルではなく、クロスエージェントフォーマットです。1つのファイルを複数のハーネス間で共有する前に、[サポートされているフォーマット](⟦4BRQ⟧)を参照してください。

### インストラクションの検証

ルールが結果に影響を与える小さなタスクをテストします。全体を通して同じハーネスとリポジトリを使用します。

1. コマンドパレット (⟦CDNA⟧) から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これは検出のチェックであり、エージェントがルールに従っているかどうかのチェックではありません。
1. インストラクションを作成した会話のガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプトでルールを繰り返さずに、小さな変更を依頼します。API の例では、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 可能であれば、応答の **References** セクションでインストラクションファイルを確認します。詳細が必要な場合は、[Agent デバッグログでリクエストを検査](⟦8NCC⟧)してください。
1. 変更とツールのクエリを確認します。この例では、ハンドラーが追加された場所、データのアクセス方法、およびエージェントが関連するテストを実行したかどうかを確認します。

結果が目標を満たしている場合は、チームが使用できるようにインストラクションファイルをレビューしてコミットします。そうでない場合は、さらにルールを追加する前に、[ファイルが検出されたか、含まれたか、従われたかを確認](⟦AS5G⟧)してください。

完全なビフォーアフターの比較とチームへのロールアウトワークフローについては、[コードベース向け AI の構成](⟦YR7C⟧)に従ってください。

## インストラクションの適用方法

スコープとアクティベーションは、異なる質問に答えます。スコープは、ガイダンスがどこで利用可能であり、誰がそれを共有するかを決定します。アクティベーションは、そのガイダンスがリクエストにいつ含まれるかを決定します。

| スコープ | 使用目的 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有されるプロジェクト規約 |
| ユーザー | ハーネスでサポートされている場所における、プロジェクトを跨いだ個人的な設定 |
| 組織 | サポートされているエクスペリエンス向けに一元管理されたガイダンス |

広く適用されるルールには、プロジェクトインストラクションから始めます。コードベースの一部のみに必要なガイダンスには、ターゲットを絞ったインストラクションを使用します。

| アクティベーション | 動作のしくみ |
|------------|--------------|
| プロジェクト全体 | ハーネスは、そのプロジェクトインストラクションファイルからのガイダンスを含めます。 |
| ファイルパターン | ⟦J8RC⟧ ファイルは ⟦EP9N⟧ を使用するか、Claude ルールファイルは ⟦B9WF⟧ を使用して、エージェントが処理するファイルに一致させます。 |
| タスクの関連性 | ローカルセッションでは、⟦TJC6⟧ により、エージェントがタスクのインストラクションファイルを読み込むかどうかを決定できます。これはパターンマッチングとは別です。 |
| 手動 | 自動検出またはアクティベーションが適切でない場合に、特定のリクエストのガイダンスを添付します。 |

⟦5Y43⟧ などのインストラクションファイルは、既存のエージェントにガイダンスを提供します。[カスタムエージェント](⟦MA5Q⟧)を定義するものではありません。コーディング規約やプロジェクトコンテキストではなく、再利用可能なマルチステップのワークフローの場合は、[エージェントスキル](⟦E4X7⟧)を検討してください。自分でワークフローを作成する前に、[カスタマイズマーケットプレイスで既存のスキルを探して](⟦3RV4⟧)ください。リポジトリ固有のコマンドと規約は、プロジェクトインストラクションに保持します。

### 1つのリクエストにインストラクションを添付する

1回限りの要件については、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

既存のインストラクションファイルを1回のリクエストで再利用するには、チャット入力の **Add Context** (⟦ET8M⟧ アイコン) を選択し、リクエストを送信する前にファイルを選択します。

## 効果的なインストラクションの作成

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを記述します。

| 代わりに | 次のように記述する |
|------------|-------|
| 良いテストを書いてください。 | ⟦2AGA⟧ からフィクスチャを再利用し、テストの変更後に ⟦7RQB⟧ を実行します。 |
| アーキテクチャに従ってください。 | HTTP ハンドラーを個別にテスト可能な状態に保つため、データベースアクセスのコードは ⟦GB4P⟧ 内に保持します。 |
| スタイルに従ってください。 | エラー文字列を返すのではなく、⟦AY5Y⟧ の既存のエラー型を使用します。 |

* **ルールを簡潔に保ちます。** 各要件に対して短い文を使用し、自明ではない制約を説明します。
* **実行可能な詳細を優先します。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避けます。** フォーマッターやリンターによって強制されるルールを重複させないでください。プロジェクト全体のファイルから特殊なガイダンスを移動します。
* **コードと一緒にインストラクションを保守します。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを注意して参照します。** 相対パスと ⟦PKKK⟧ 区切り文字を使用した Markdown リンクを使用します。リンクは、ドキュメントの内容がモデルに届くことを保証するものではありません。[参照ファイルの動作](⟦JP57⟧)を確認してください。

### 競合するインストラクションの解決

個人的なガイダンス、リポジトリのガイダンス、および組織のガイダンスの間で、共有要件の一貫性を保ちます。普遍的な優先順位に依存しないでください。[組み合わせのルールはハーネスによって異なります](⟦DCSM⟧)。

個人的なインストラクションが一方のライブラリを要求し、リポジトリが別のライブラリを要求している場合は、競合する個人的なルールを削除するか、範囲を狭めます。補正するためにもう1つルールを追加しないでください。競合を解決した後に、新しいチャットで同じ代表的なタスクを繰り返します。

## プロジェクトおよび個人的なインストラクションの管理

Agent Customizations エディターの **Instructions** に戻って、既存のインストラクションを検索および編集します。個人的なインストラクションを追加するには、**User** の横にある ⟦RCEE⟧ を選択します。ハーネスでサポートされている名前と保存場所のプロンプトに従い、ファイルを保存し、そのハーネスを使用した新しいチャットで検証します。

プロジェクトを跨いだ個人的な設定には、ユーザースコープを使用します。チームも望んでいない限り、個人の応答設定を共有プロジェクトファイルに入れないでください。場所と同期の制限については、[ユーザーインストラクション](⟦X2DE⟧)を参照してください。

また、関連するエージェント、スキル、またはツールと一緒に、[エージェントプラグイン](⟦EB44⟧)内のルールコンポーネントとしてインストラクションを配信することもできます。サポートは、選択したハーネスとプラグインフォーマットによって異なります。クライアント間でバンドルを共有する前に、[プラグインの互換性](⟦MWJS⟧)を確認してください。

## インストラクションのトラブルシューティング

ガイダンスを変更する前に、失敗のステージを特定します。

| 観察される現象 | 確認すべき事項 |
|------------------|---------------|
| ファイルが Customizations エディターにリストされない。 | 選択したハーネス、ファイル名、サポートされている場所、およびセッションに変更を含むフォルダーを使用しているかどうかを確認します。 |
| ファイルが検出されたが、タスクに含まれない。 | フロントマターのエラーとアクティベーション条件を確認します。一致するファイルをテストするか、手動でインストラクションを添付します。ローカルの場合は、該当する[検出設定](⟦Y3BW⟧)を確認します。 |
| ファイルが含まれているが、結果がそれに従わない。 | 矛盾するルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返し、実際の変更とツールのクエリを比較します。 |

可能であれば、応答の **References** セクションは、コンプライアンスではなく包含の確認に役立ちます。詳細な証拠については、[インストラクションの診断](⟦SJC8⟧)に従ってください。問題を再現する前にロギングを準備します。
