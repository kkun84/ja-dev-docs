# Use custom instructions in VS Code

Custom instructions give an agent reusable guidance about your project, such as where to add code, which libraries to use, and which tests to run. Store this guidance in Markdown files instead of repeating it in every prompt, and share project instructions through source control.

Start with one convention the agent repeatedly misses. Create instructions in the [Agent Customizations editor](⟦ZSVQ⟧), then test their effect in a new chat before adding more targeted guidance. For supported locations, file syntax, and settings, see the [Custom instructions reference](⟦A3R4⟧).

Instructions guide the model. They don't guarantee compliance or replace tests, code review, or security controls. They don't apply to [inline suggestions](⟦VVB9⟧) as you type.

## Get started with project instructions

Open the repository root and [select the agent harness](⟦4DJ5⟧) you intend to use. The harness determines which instruction files it reads. Choosing a Claude model in a Copilot session, for example, doesn't switch to the Claude harness.

For this first setup, work in the current folder rather than a new worktree so the test session can access your uncommitted instructions.

### Verify your instructions

Test a small task where the rules affect the outcome. Use the same harness and repository throughout:

1. Run **Chat: Open Customizations** from the Command Palette (⟦R245⟧). Select **Instructions** and confirm that the file is listed. This checks discovery, not whether the agent follows the rules.
1. Start a new chat so the test doesn't depend on guidance from the conversation that created the instructions.
1. Ask for a small change without repeating the rules in the prompt. For the API example, ask the agent to add an endpoint using the project's existing patterns.
1. Check the response's **References** section, where available, for the instructions file. If you need more detail, [inspect the request in Agent Debug Logs](⟦PSP2⟧).
1. Review the changes and tool activity. For the example, check where the handler was added, how it accesses data, and whether the agent ran the relevant tests.

If the result meets your goal, review and commit the instructions file so your team can use it. If not, [identify whether the file was discovered, included, or followed](⟦MF75⟧) before adding more rules.

For a complete before-and-after comparison and team rollout workflow, follow [Configure AI for your codebase](⟦NRTZ⟧).

## How instructions apply

Scope and activation answer different questions. Scope determines where guidance is available and who shares it. Activation determines when that guidance is included in a request.

| Scope | Use it for |
|-------|------------|
| Workspace or repository | Project conventions shared with contributors through source control |
| User | Personal preferences across projects, in a location supported by your harness |
| Organization | Centrally managed guidance for supported experiences |

Start with project instructions for rules that apply broadly. Use targeted instructions for guidance needed only in part of your codebase.

| Activation | How it works |
|------------|--------------|
| Project-wide | The harness includes guidance from its project instruction files. |
| File pattern | An ⟦YGNJ⟧ file uses ⟦ZJWT⟧, or a Claude rules file uses ⟦P7K6⟧, to match files the agent works with. |
| Task relevance | In Local sessions, a ⟦3CZT⟧ lets the agent decide whether to read an instructions file for the task. This is separate from pattern matching. |
| Manual | Attach guidance for a particular request when automatic discovery or activation isn't appropriate. |

An instruction file such as ⟦JAEC⟧ provides guidance to an existing agent. It doesn't define a [custom agent](⟦SDXQ⟧). For a reusable multi-step workflow rather than coding conventions or project context, consider an [agent skill](⟦BHGZ⟧). [Look for an existing skill in the Customization Marketplace](⟦AND2⟧) before writing the workflow yourself. Keep repository-specific commands and conventions in your project instructions.

### Attach instructions to one request

For a one-time requirement, put the guidance in your prompt rather than creating a shared rule.

To reuse an existing instructions file for one request, select **Add Context** (⟦FWYW⟧ icon) in the chat input and select the file before sending the request.

## Write effective instructions

Write rules that help the agent make project-specific decisions, rather than describing everything in the repository.

| Instead of | Write |
|------------|-------|
| Write good tests. | Reuse fixtures from ⟦GZBS⟧ and run ⟦THMB⟧ after changing a test. |
| Follow the architecture. | Keep database access in ⟦6RYR⟧ so HTTP handlers remain independently testable. |
| Follow our style. | Use the existing error type in ⟦KPPM⟧ rather than returning an error string. |

* **Keep rules concise.** Use a short statement for each requirement and explain non-obvious constraints.
* **Prefer actionable details.** Name the command, directory, library, or existing example the agent should use.
* **Avoid unnecessary context.** Don't duplicate rules enforced by formatters or linters. Move specialized guidance out of the project-wide file.
* **Maintain instructions with the code.** Review changes through source control and update rules when commands, architecture, or dependencies change.
* **Reference supporting documentation carefully.** Use Markdown links with relative paths and ⟦SKHZ⟧ separators. A link doesn't guarantee that the document's contents reach the model. Check [referenced-file behavior](⟦NY2M⟧).

### Resolve conflicting instructions

Keep shared requirements consistent across personal, repository, and organization guidance. Don't rely on a universal precedence order: [combination rules differ by harness](⟦3WYX⟧).

If a personal instruction requests one library and the repository requires another, remove or narrow the conflicting personal rule. Don't add another rule to compensate. Repeat the same representative task in a new chat after resolving the conflict.

## Manage project and personal instructions

Return to **Instructions** in the Agent Customizations editor to find and edit existing instructions. To add personal instructions, select ⟦9WMP⟧ next to **User**. Follow the prompts for a name and storage location supported by your harness, save the file, and verify it in a new chat with that harness.

Use user scope for personal preferences across projects. Don't put your individual response preferences in a shared project file unless your team wants them too. For locations and synchronization limits, see [user instructions](⟦PFMF⟧).

You can also distribute instructions as rule components in an [agent plugin](⟦EEVT⟧), alongside related agents, skills, or tools. Support depends on the selected harness and plugin format. Check [plugin compatibility](⟦WBRN⟧) before sharing the bundle across clients.

## Troubleshoot instructions

Identify the failure stage before changing your guidance:

| What you observe | What to check |
|------------------|---------------|
| The file isn't listed in the Customizations editor. | Confirm the selected harness, file name, supported location, and whether the session uses the folder containing your changes. |
| The file is discovered but isn't included for the task. | Check frontmatter errors and activation conditions. Test a matching file, or attach the instructions manually. For Local, check the applicable [discovery settings](⟦3356⟧). |
| The file is included but the result doesn't follow it. | Check for contradictory or vague rules. Clarify one rule, repeat the task in a new chat, and compare the actual changes and tool activity. |

The response's **References** section, where available, helps check inclusion, not compliance. For detailed evidence, follow [instruction diagnostics](⟦YXQA⟧). Prepare logging before reproducing the issue.
