# VS Code でカスタム指示を使用する

カスタム指示を使用すると、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供できます。このガイダンスをすべてのプロンプトで繰り返すのではなく、Markdown ファイルに保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている 1 つの規則から始めます。⟦WJ5W⟧ で指示を作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、設定については、⟦D6QC⟧ を参照してください。

指示はモデルを誘導するものです。これらはコンプライアンスを保証するものではなく、テスト、コードレビュー、セキュリティ制御の代わりにもなりません。入力時の ⟦XJTQ⟧ には適用されません。

## プロジェクトの指示を開始する

リポジトリのルートを開き、使用する ⟦5C2V⟧ を選択します。ハーネスによって、どの指示ファイルが読み取られるかが決まります。たとえば、Copilot セッションで Claude モデルを選択しても、Claude ハーネスには切り替わりません。

最初のセットアップでは、テストセッションからコミットされていない指示にアクセスできるようにするため、新しいワークトレードではなく現在のフォルダーで作業します。

### プロジェクトの指示を作成する

1. コマンドパレット (⟦4FJ7⟧) から **Chat: Open Customizations** を実行して Agent Customizations エディターを開き、**Instructions** タブを選択します。

1. プロジェクトの指示ファイルを追加するには、⟦F2R7⟧ の横にある ⟦F2R7⟧ を選択し、⟦JMC4⟧ や ⟦KFMH⟧ など、ハーネス用に提案されたプロジェクトの指示ファイルを選択します。エディターによって、ワークスペースにファイルが作成されるか、ファイルが開きます。

   リポジトリにすでにプロジェクトの指示ファイルがある場合は、競合するコピーを作成する代わりにそれを開いてください。

1. 繰り返し発生する問題に対処するいくつかの具体的なルールを追加します。たとえば、Node.js API プロジェクトでは次の指示を使用する場合があります。パスとテストコマンドを、リポジトリで機能するものに置き換えてください。

   ⟦P444⟧

1. ファイルを保存します。これらのプロジェクトの指示ファイルにフロントマターは必要ありません。

#### ファイルを直接作成する

Agent Customizations エディター以外の場所でファイルを作成する場合は、ハーネスでサポートされているプロジェクトの指示ファイルを使用します。以下のパスはリポジトリのルートからの相対パスです。必要に応じて、存在しないフォルダーを作成します。

| ハーネス | プロジェクトの指示ファイル |
|---------|---------------------------|
| Copilot | ⟦3N8K⟧ または ⟦R8BD⟧ |
| Anthropic Claude | ⟦XRG8⟧ |
| OpenAI Codex | ⟦KXWS⟧ |
| Local ⟦7233⟧ | ⟦VM5E⟧ または ⟦7GRZ⟧ |

ルールを追加してファイルを保存し、以下で説明するように検証します。⟦R4BF⟧ は Codex 専用のファイルではなく、エージェント横断的な形式です。1つのファイルを複数のハーネス間で共有する前に、⟦FHEK⟧ を参照してください。

### 指示を検証する

ルールが結果に影響を与える小さなタスクをテストします。最初から最後まで同じハーネスとリポジトリを使用します。

1. コマンドパレット (⟦RBXC⟧) から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これは、エージェントがルールに従っているかどうかではなく、検出されるかどうかを確認するものです。
1. 指示を作成した会話のガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプトでルールを繰り返さずに、小さな変更を依頼します。API の例では、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 可能であれば、応答の **References** セクションで指示ファイルを確認します。詳細が必要な場合は、⟦27M8⟧ を参照してください。
1. 変更とツールのクエリを確認します。例の場合、ハンドラーが追加された場所、データのアクセス方法、エージェントが関連するテストを実行したかどうかを確認します。

結果が目標を満たしている場合は、チームが使用できるように指示ファイルをレビューしてコミットします。満たしていない場合は、ルールを追加する前に [ファイルが検出されたか、含まれたか、従われたかを確認します](⟦8G6T⟧)。

ビフォーアフターの完全な比較とチームへの展開ワークフローについては、⟦J574⟧ をフォローしてください。

## 指示の適用方法

スコープと有効化は異なる疑問に答えます。スコープは、ガイダンスがどこで利用可能であり、誰がそれを共有するかを決定します。有効化は、そのガイダンスがリクエストにいつ含まれるかを決定します。

| スコープ | 使用目的 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有されるプロジェクトの規則 |
| ユーザー | ハーネスでサポートされている場所における、プロジェクトをまたいだ個人的な設定 |
| 組織 | サポートされているエクスペリエンス向けに一元管理されたガイダンス |

広範囲に適用されるルールについては、プロジェクトの指示から始めます。コードベースの一部のみで必要なガイダンスについては、ターゲットを絞った指示を使用します。

| 有効化 | 動作の仕組み |
|------------|--------------|
| プロジェクト全体 | ハーネスは、プロジェクトの指示ファイルからガイダンスを含めます。 |
| ファイルパターン | ⟦BEHF⟧ ファイルは ⟦VADV⟧ を使用するか、Claude ルールファイルは ⟦2V6Y⟧ を使用して、エージェントが処理するファイルに一致させます。 |
| タスクの関連性 | Local セッションでは、⟦K4FQ⟧ により、エージェントがタスクの指示ファイルを読み取るかどうかを決定できます。これはパターンマッチングとは別です。 |
| 手動 | 自動検出または有効化が適切でない特定のリクエストにガイダンスを添付します。 |

⟦73N9⟧ などの指示ファイルは、既存のエージェントにガイダンスを提供します。⟦NCSE⟧ を定義するものではありません。コーディング規則やプロジェクトコンテキストではなく、再利用可能なマルチステップのワークフローについては、⟦R8ZE⟧ を検討してください。ワークフローを自分で記述する前に、⟦RKPK⟧ を探してください。リポジトリ固有のコマンドと規則は、プロジェクトの指示に記述してください。

### 1つのリクエストに指示を添付する

1回限りの要件の場合は、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

1つのリクエストで既存の指示ファイルを再利用するには、チャット入力の **Add Context** (⟦FV8V⟧ アイコン) を選択し、リクエストを送信する前にファイルを選択します。

## 効果的な指示を記述する

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを記述します。

| 代わりに | 次のように記述 |
|------------|-------|
| 良いテストを書く。 | ⟦E2ZS⟧ のフィクスチャを再利用し、テストの変更後に ⟦2W49⟧ を実行する。 |
| アーキテクチャに従う。 | HTTP ハンドラーを個別にテスト可能な状態に保つため、データベースアクセスを ⟦RX8F⟧ に保持する。 |
| スタイルに従う。 | エラー文字列を返すのではなく、⟦54GP⟧ の既存のエラータイプを使用する。 |

* **ルールを簡潔に保つ。** 各要件に対して短い文を使用し、自明ではない制約については説明します。
* **実行可能な詳細を優先する。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避ける。** フォーマッターやリンターによって強制されるルールを重複させないでください。特殊なガイダンスはプロジェクト全体のファイルから移動させます。
* **コードと一緒に指示を維持する。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを慎重に参照する。** 相対パスと ⟦HVKC⟧ 区切り文字を使用した Markdown リンクを使用します。リンクがあるからといって、ドキュメントの内容がモデルに届くことが保証されるわけではありません。[参照されたファイルの動作](⟦QHCH⟧)を確認してください。

### 競合する指示を解決する

共有要件は、個人、リポジトリ、組織のガイダンス間で一貫性を保つ必要があります。普遍的な優先順位の順序に依存しないでください。[組み合わせ規則はハーネスによって異なります](⟦XYAH⟧)。

個人の指示が一方のライブラリを要求し、リポジトリが別のライブラリを要求している場合は、競合している個別のルールを削除するか、範囲を狭めます。補正するために別のルールを追加しないでください。競合を解決した後、新しいチャットで同じ代表的なタスクを繰り返します。

## プロジェクトと個人の指示を管理する

Agent Customizations エディターの **Instructions** に戻って、既存の指示を検索および編集します。個人の指示を追加するには、**User** の横にある ⟦WMST⟧ を選択します。ハーネスでサポートされている名前と保存場所のプロンプトに従い、ファイルを保存し、そのハーネスを使用した新しいチャットで検証します。

プロジェクト間で個人的な設定を使用するには、ユーザースコープを使用します。チームが望んでいる場合を除き、個人の応答の好みを共有プロジェクトファイルに入れないでください。場所と同期の制限については、⟦6Z4X⟧ を参照してください。

また、関連するエージェント、スキル、ツールとともに、⟦3G66⟧ のルールコンポーネントとして指示を配布することもできます。サポートは、選択したハーネスとプラグインの形式によって異なります。バンドルをクライアント間で共有する前に、⟦S459⟧ を確認してください。

## 指示のトラブルシューティング

ガイダンスを変更する前に、障害の発生段階を特定します。

| 観測される現象 | 確認すべきこと |
|------------------|---------------|
| ファイルが Customizations エディターにリストされない。 | 選択したハーネス、ファイル名、サポートされている場所、およびセッションに変更が含まれるフォルダーを使用しているかどうかを確認します。 |
| ファイルが検出されているが、タスクに含まれていない。 | フロントマターのエラーと有効化条件を確認します。一致するファイルをテストするか、指示を手動で添付します。Local の場合は、適用される [検出設定](⟦7DM6⟧)を確認します。 |
| ファイルが含まれているが、結果がそれに従っていない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返して、実際の変更とツールのクエリを比較します。 |

可能であれば、応答の **References** セクションは、コンプライアンスではなく、インクルージョンの確認に役立ちます。詳細な証拠については、⟦VNVR⟧ をフォローしてください。問題を再現する前にロギングを準備します。
