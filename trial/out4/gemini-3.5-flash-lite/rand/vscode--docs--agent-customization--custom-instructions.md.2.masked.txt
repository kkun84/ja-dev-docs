# ⟦JGN5⟧ でカスタム指示を使用する

カスタム指示は、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供します。このガイダンスをすべてのプロンプトで繰り返すのではなく、Markdownファイルに保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている1つの規約から始めます。[Agent Customizations editor](⟦PSP2⟧)で指示を作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、および設定については、[Custom instructions reference](⟦MF75⟧)を参照してください。

指示はモデルを誘導するものです。これらは遵守を保証したり、テスト、コードレビュー、セキュリティ制御を置き換えたりするものではありません。入力時の[inline suggestions](⟦NRTZ⟧)には適用されません。

## プロジェクト指示の概要

リポジトリのルートを開き、使用する予定の[agent harness](⟦SDXQ⟧)を選択します。ハーネスによって、読み取る指示ファイルが決まります。たとえば、⟦A7H9⟧ セッションで Claude モデルを選択しても、Claude ハーネスには切り替わりません。

最初のセットアップでは、テストセッションがコミットされていない指示にアクセスできるようにするため、新しいワークツリーではなく現在のフォルダで作業します。

### プロジェクト指示を作成する

1. コマンドパレット（⟦5GVG⟧）から **Chat: Open Customizations** を実行して Agent Customizations エディタを開き、**Instructions** タブを選択します。

1. プロジェクト指示ファイルを追加するには、**Workspace** の横にある ⟦8W9Q⟧ を選択し、⟦AAE9⟧ や ⟦5YQA⟧ など、ハーネスに対して提供されているプロジェクト指示ファイルを選択します。エディタはワークスペース内にファイルを作成または開きます。

   リポジトリにすでにプロジェクト指示ファイルが存在する場合は、競合するコピーを作成する代わりにそれを開きます。

1. 繰り返し発生する問題に対処するいくつかの具体的なルールを追加します。たとえば、Node.js API プロジェクトでは次の指示を使用する場合があります。パスとテストコマンドを、リポジトリで機能するものに置き換えてください。

   ⟦HK7E⟧

1. ファイルを保存します。これらのプロジェクト指示ファイルにフロントマターは必要ありません。

#### ファイルを直接作成する

Agent Customizations エディタの外部でファイルを作成したい場合は、ハーネスでサポートされているプロジェクト指示ファイルを使用してください。以下のパスはリポジトリのルートからの相対パスです。必要に応じて欠落しているフォルダを作成してください。

| ハーネス | プロジェクト指示ファイル |
|---------|---------------------------|
| ⟦SD5P⟧ | ⟦BAVF⟧ または ⟦WDQ8⟧ |
| ⟦DSDR⟧ | ⟦GAJG⟧ |
| ⟦XJ7P⟧ | ⟦R245⟧ |
| Local ⟦YGNJ⟧ | ⟦ZJWT⟧ または ⟦P7K6⟧ |

ルールを追加し、ファイルを保存して、以下に説明するように検証します。⟦3CZT⟧ はクロスエージェントフォーマットであり、Codex 専用のファイルではありません。1つのファイルを複数のハーネス間で共有する前に、[supported formats](⟦BHGZ⟧)を参照してください。

### 指示を検証する

ルールが結果に影響する小さなタスクをテストします。一貫して同じハーネスとリポジトリを使用してください。

1. コマンドパレット（⟦JAEC⟧）から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これは、エージェントがルールに従っているかどうかではなく、検出されるかどうかを確認するものです。
1. 指示を作成した会話のガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプトでルールを繰り返さずに、小さな変更を依頼します。API の例については、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 利用可能な場合は、応答の **References** セクションで指示ファイルを確認します。詳細が必要な場合は、[inspect the request in Agent Debug Logs](⟦AND2⟧)を行ってください。
1. 変更内容とツールの動作を確認します。例では、ハンドラーがどこに追加されたか、データにどのようにアクセスしているか、エージェントが関連するテストを実行したかどうかを確認します。

結果が目標を満たしている場合は、チームが使用できるように指示ファイルをレビューしてコミットします。満たしていない場合は、さらにルールを追加する前に、[identify whether the file was discovered, included, or followed](⟦EYWS⟧)を行ってください。

ビフォーアフターの完全な比較とチームへの展開ワークフローについては、[Configure AI for your codebase](⟦FXCY⟧)に従ってください。

## 指示の適用方法

スコープ（Scope）とアクティベーション（Activation）は、異なる質問に答えます。スコープは、ガイダンスがどこで利用可能であり、誰がそれを共有するかを決定します。アクティベーションは、そのガイダンスがリクエストにいつ含まれるかを決定します。

| スコープ | 用途 |
|-------|------------|
| Workspace または repository | ソース管理を通じてコントリビューターと共有されるプロジェクト規約 |
| User | ハーネスでサポートされている場所における、プロジェクト横断的な個人的好み |
| Organization | サポートされているエクスペリエンス向けに一元管理されたガイダンス |

幅広く適用されるルールについては、プロジェクト指示から始めます。コードベースの一部のみで必要なガイダンスについては、ターゲットを絞った指示を使用します。

| アクティベーション | 仕組み |
|------------|--------------|
| Project-wide | ハーネスには、そのプロジェクト指示ファイルからのガイダンスが含まれます。 |
| File pattern | ⟦VQ84⟧ ファイルは ⟦ZRHK⟧ を使用するか、Claude ルールファイルは ⟦ER3C⟧ を使用して、エージェントが操作するファイルに一致させます。 |
| Task relevance | Local セッションでは、⟦5ZKS⟧ により、エージェントがタスクの指示ファイルを読み取るかどうかを決定できます。これはパターンマッチングとは別です。 |
| Manual | 自動検出またはアクティベーションが適切ではない特定のリクエストに対して、ガイダンスを添付します。 |

⟦QXJS⟧ などの指示ファイルは、既存のエージェントにガイダンスを提供します。[custom agent](⟦NY2M⟧)を定義するものではありません。コーディング規約やプロジェクトコンテキストではなく、再利用可能なマルチステップワークフローの場合は、[agent skill](⟦3WYX⟧)を検討してください。[Look for an existing skill in the Customization Marketplace](⟦PFMF⟧)で既存のスキルを探してから、自分でワークフローを作成してください。リポジトリ固有のコマンドと規約は、プロジェクト指示に記述してください。

### 1つのリクエストに指示を添付する

1回限りの要件については、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

1つのリクエストのために既存の指示ファイルを再利用するには、チャット入力の **Add Context**（⟦SKHZ⟧ アイコン）を選択し、リクエストを送信する前にファイルを選択します。

## 効果的な指示を記述する

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを記述します。

| 代わりに | 次のように記述します |
|------------|-------|
| Write good tests. | ⟦9WMP⟧ からフィクスチャを再利用し、テストを変更した後に ⟦ZSVQ⟧ を実行します。 |
| Follow the architecture. | HTTP ハンドラーが独立してテスト可能な状態を維持できるように、データベースアクセスを ⟦A3R4⟧ 内に保持します。 |
| Follow our style. | エラー文字列を返すのではなく、⟦VVB9⟧ 内の既存のエラータイプを使用します。 |

* **ルールを簡潔に保ちます。** 各要件に対して短いステートメントを使用し、自明ではない制約については説明します。
* **アクション可能な詳細を優先します。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避けます。** フォーマッタやリンターによって強制されるルールを重複させないでください。プロジェクト全体のファイルから特殊なガイダンスを移動します。
* **コードと一緒に指示を保守します。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを注意深く参照します。** 相対パスと ⟦4DJ5⟧ セパレータを使用する Markdown リンクを使用します。リンクは、ドキュメントの内容がモデルに届くことを保証するものではありません。[referenced-file behavior](⟦VMGW⟧)を確認してください。

### 競合する指示を解決する

個人的なガイダンス、リポジトリのガイダンス、組織のガイダンスの間で、共有される要件を一貫性のあるものに保ちます。普遍的な優先順位の順序に依存しないでください。[combination rules differ by harness](⟦XM8F⟧)です。

個人的な指示が一方のライブラリを要求し、リポジトリが別のライブラリを要求している場合は、競合する個人的なルールを削除するか、範囲を狭めます。補正のために別のルールを追加しないでください。競合を解決した後、新しいチャットで同じ代表的なタスクを繰り返します。

## プロジェクトおよび個人的な指示を管理する

Agent Customizations エディタの **Instructions** に戻り、既存の指示を見つけて編集します。個人的な指示を追加するには、**User** の隣にある ⟦EP5D⟧ を選択します。ハーネスでサポートされている名前と保存場所のプロンプトに従い、ファイルを保存し、そのハーネスを使用した新しいチャットで検証します。

プロジェクト横断的な個人的な好みには、ユーザーパースペクティブを使用します。チームが望んでいるのでない限り、個人の応答の好みを共有プロジェクトファイルに入れないでください。場所と同期の制限については、[user instructions](⟦2QSC⟧)を参照してください。

関連するエージェント、スキル、またはツールとともに、[agent plugin](⟦2MBM⟧)内のルールコンポーネントとして指示を配布することもできます。サポートは、選択したハーネスとプラグインフォーマットによって異なります。クライアント間でバンドルを共有する前に、[plugin compatibility](⟦C9W3⟧)を確認してください。

## 指示のトラブルシューティング

ガイダンスを変更する前に、失敗のステージを特定します。

| 観察される内容 | 確認すべきこと |
|------------------|---------------|
| ファイルが Customizations エディタにリストされない。 | 選択したハーネス、ファイル名、サポートされている場所、およびセッションが変更を含むフォルダを使用しているかどうかを確認します。 |
| ファイルは検出されたが、タスクに含まれていない。 | フロントマターのエラーとアクティベーション条件を確認します。一致するファイルをテストするか、手動で指示を添付します。Local の場合は、適用可能な [discovery settings](⟦KYCZ⟧)を確認してください。 |
| ファイルは含まれているが、結果がそれに従っていない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返し、実際の変更とツールの動作を比較します。 |

利用可能な場合の応答の **References** セクションは、コンプライアンスではなく、含まれているかどうかを確認するのに役立ちます。詳細な証拠については、[instruction diagnostics](⟦3DXV⟧)に従ってください。問題を再現する前にログの準備をします。
