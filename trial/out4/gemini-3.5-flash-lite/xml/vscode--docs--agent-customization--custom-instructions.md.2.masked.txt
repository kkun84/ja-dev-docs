# <x id="JGN5"/> でカスタム指示を使用する

カスタム指示を使用すると、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに与えることができます。すべてのプロンプトで繰り返し指定するのではなく、このガイダンスを Markdown ファイルに保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている1つの規約から始めます。[Agent Customizations エディタ](<x id="PSP2"/>)で指示を作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、および設定については、[Custom instructions のリファレンス](<x id="MF75"/>)を参照してください。

指示はモデルをガイドするものです。準拠を保証するものではなく、テスト、コードレビュー、またはセキュリティ制御の代わりにもなりません。入力中の[インラインサジェスト](<x id="NRTZ"/>)には適用されません。

## プロジェクト指示の開始

リポジトリのルートを開き、使用する予定の[エージェントハーネスを選択します](<x id="SDXQ"/>)。ハーネスによって、どの指示ファイルが読み取られるかが決まります。たとえば、<x id="A7H9"/> セッションで Claude モデルを選択しても、Claude ハーネスには切り替わりません。

最初のセットアップでは、テストセッションからコミットされていない指示にアクセスできるようにするため、新しいワークツリーではなく現在のフォルダーで作業します。

### プロジェクト指示を作成する

1. コマンドパレット (<x id="5GVG"/>) から **Chat: Open Customizations** を実行して Agent Customizations エディタを開き、**Instructions** タブを選択します。

1. プロジェクト指示ファイルを追加するには、**Workspace** の横にある <x id="8W9Q"/> を選択し、<x id="AAE9"/> や <x id="5YQA"/> など、お使いのハーネス用に提示されたプロジェクト指示ファイルを選択します。エディタによって、ワークスペース内にファイルが作成されるか、既存のファイルが開きます。

   リポジトリにすでにプロジェクト指示ファイルが存在する場合は、競合するコピーを作成するのではなく、既存のファイルを開いてください。

1. 繰り返し発生する問題に対処する具体的なルールをいくつか追加します。たとえば、Node.js の API プロジェクトでは、次の指示を使用できます。パスとテストコマンドは、お使いのリポジトリで動作するものに置き換えてください。

   <x id="HK7E"/>

1. ファイルを保存します。これらのプロジェクト指示ファイルにフロントマターは必要ありません。

#### ファイルを直接作成する

Agent Customizations エディタ外でファイルを作成したい場合は、お使いのハーネスでサポートされているプロジェクト指示ファイルを使用してください。以下のパスはリポジトリのルートからの相対パスです。必要に応じて、存在しないフォルダーを作成してください。

| ハーネス | プロジェクト指示ファイル |
|---------|---------------------------|
| <x id="SD5P"/> | <x id="BAVF"/> または <x id="WDQ8"/> |
| <x id="DSDR"/> | <x id="GAJG"/> |
| <x id="XJ7P"/> | <x id="R245"/> |
| ローカルの <x id="YGNJ"/> | <x id="ZJWT"/> または <x id="P7K6"/> |

ルールを追加し、ファイルを保存して、以下に説明するように検証します。<x id="3CZT"/> は Codex 専用のファイルではなく、クロスエージェント形式です。1つのファイルを複数のハーネス間で共有する前に、[サポートされている形式](<x id="BHGZ"/>)を参照してください。

### 指示を検証する

ルールが結果に影響するような小さなタスクをテストします。最初から最後まで同じハーネスとリポジトリを使用します。

1. コマンドパレット (<x id="JAEC"/>) から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これにより、エージェントがルールに従っているかどうかではなく、検出されるかどうかが確認されます。
1. 指示を作成した会話のガイダンスにテストが依存しないよう、新しいチャットを開始します。
1. プロンプト内でルールを繰り返さずに、小さな変更を依頼します。API の例では、プロジェクトの既存のパターンを使用してエンドポイントを追加するようエージェントに依頼します。
1. 可能であれば、応答の **References** セクションで指示ファイルを確認します。さらに詳細が必要な場合は、[Agent デバッグログでリクエストを検査します](<x id="AND2"/>)。
1. 変更内容とツールの動作を確認します。例の場合は、ハンドラーが追加された場所、データのアクセス方法、およびエージェントが関連するテストを実行したかどうかを確認します。

結果が目的に合致している場合は、チームが使用できるように指示ファイルをレビューしてコミットします。そうでない場合は、さらにルールを追加する前に、[ファイルが検出されたか、含まれたか、従われたかを確認します](<x id="EYWS"/>)。

変更前後の完全な比較とチームへのロールアウトワークフローについては、[コードベース向け AI の構成](<x id="FXCY"/>)に従ってください。

## 指示の適用方法

スコープと有効化は異なる疑問に答えるものです。スコープは、ガイダンスがどこで利用可能か、誰がそれを共有するかを決定します。有効化は、そのガイダンスがリクエストにいつ含まれるかを決定します。

| スコープ | 用途 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有されるプロジェクト規約 |
| ユーザー | ハーネスでサポートされている場所における、プロジェクト横断的な個人の好み |
| 組織 | サポートされているエクスペリエンス向けに一元管理されたガイダンス |

広範に適用されるルールにはプロジェクト指示から始めます。コードベースの一部のみで必要なガイダンスには、ターゲットを絞った指示を使用します。

| 有効化 | 動作の仕組み |
|------------|--------------|
| プロジェクト全体 | ハーネスには、そのプロジェクト指示ファイルからのガイダンスが含まれます。 |
| ファイルパターン | エージェントが操作するファイルに一致させるため、<x id="VQ84"/> ファイルで <x id="ZRHK"/> を使用するか、Claude ルールファイルで <x id="ER3C"/> を使用します。 |
| タスクの関連性 | ローカルセッションでは、<x id="5ZKS"/> により、エージェントがタスク用の指示ファイルを読み込むかどうかを決定できます。これはパターンマッチングとは別です。 |
| 手動 | 自動検出または有効化が適切でない特定のりクエストにガイダンスを添付します。 |

<x id="QXJS"/> などの指示ファイルは、既存のエージェントにガイダンスを提供します。[カスタムエージェント](<x id="NY2M"/>)を定義するものではありません。コーディング規約やプロジェクトコンテキストではなく、再利用可能なマルチステップのワークフローが必要な場合は、[エージェントスキル](<x id="3WYX"/>)を検討してください。ワークフローを自分で作成する前に、[カスタマイズマーケットプレイスで既存のスキルを探してください](<x id="PFMF"/>)。リポジトリ固有のコマンドや規約は、プロジェクト指示に記述してください。

### 1回のリクエストに指示を添付する

1回限りの要件については、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

既存の指示ファイルを1回のリクエストで再利用するには、チャット入力の **Add Context** (<x id="SKHZ"/> アイコン) を選択し、リクエストを送信する前にそのファイルを選択します。

## 効果的な指示を記述する

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを記述します。

| 代わりに | 次のように記述する |
|------------|-------|
| 良いテストを書く。 | <x id="9WMP"/> のフィクスチャを再利用し、テストを変更した後に <x id="ZSVQ"/> を実行する。 |
| アーキテクチャに従う。 | HTTP ハンドラーを独立してテスト可能な状態に保つため、データベースアクセスを <x id="A3R4"/> 内に維持する。 |
| 当社のスタイルに従う。 | エラー文字列を返すのではなく、<x id="VVB9"/> の既存のエラー型を使用する。 |

* **ルールを簡潔に保つ。** 各要件に対して短い文を使用し、自明ではない制約については説明します。
* **実行可能な詳細を優先する。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避ける。** フォーマッタやリンターによって強制されるルールを重複させないでください。プロジェクト全体のファイルから専門的なガイダンスを移動します。
* **コードと一緒に指示を保守する。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを慎重に参照する。** 相対パスと <x id="4DJ5"/> 区切り文字を使用した Markdown リンクを使用します。リンクがあるからといって、ドキュメントの内容がモデルに確実に届くわけではありません。[参照されたファイルの動作](<x id="VMGW"/>)を確認してください。

### 競合する指示を解決する

個人、リポジトリ、組織のガイダンスの間で、共有要件が一貫していることを確認します。普遍的な優先順位の順序に依存しないでください。[組み合わせのルールはハーネスによって異なります](<x id="XM8F"/>)。

個人の指示で特定のライブラリが要求され、リポジトリで別のライブラリが必要とされる場合は、競合する個人のルールを削除するか狭めます。補正するために別のルールを追加しないでください。競合を解決した後に、同じ代表的なタスクを新しいチャットで繰り返します。

## プロジェクト指示と個人指示を管理する

Agent Customizations エディタの **Instructions** に戻って、既存の指示を見つけて編集します。個人用の指示を追加するには、**User** の横にある <x id="EP5D"/> を選択します。お使いのハーネスでサポートされている名前と保存場所のプロンプトに従い、ファイルを保存して、そのハーネスを使用した新しいチャットで検証します。

プロジェクト横断的な個人の好みには、ユーザーのスコープを使用します。チームが望んでいる場合を除き、個人の応答の好み共有プロジェクトファイルに入れないでください。場所と同期の制限については、[ユーザー指示](<x id="2QSC"/>)を参照してください。

関連するエージェント、スキル、またはツールと一緒に、[エージェントプラグイン](<x id="2MBM"/>)内のルールコンポーネントとして指示を配布することもできます。サポートは、選択したハーネスとプラグインの形式によって異なります。クライアント間でバンドルを共有する前に、[プラグインの互換性](<x id="C9W3"/>)を確認してください。

## 指示のトラブルシューティング

ガイダンスを変更する前に、障害が発生している段階を特定します。

| 観測される現象 | 確認すべきこと |
|------------------|---------------|
| カスタマイズエディタにファイルがリストされない。 | 選択されたハーネス、ファイル名、サポートされている場所、およびセッションが変更を含むフォルダーを使用しているかどうかを確認します。 |
| ファイルは検出されるが、タスクに含まれない。 | フロントマターのエラーと有効化の条件を確認します。一致するファイルをテストするか、指示を手動で添付します。ローカルの場合は、該当する[検出設定](<x id="KYCZ"/>)を確認します。 |
| ファイルが含まれているが、結果がそれに従わない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返して、実際の変更とツールの動作を比較します。 |

可能であれば、応答の **References** セクションは、コンプライアンスではなく、包含の確認に役立ちます。詳細な証拠については、[指示の診断](<x id="3DXV"/>)に従ってください。問題を再現する前にロギングの準備をします。
