# ⟦L6:variables.product.prodname_vscode_shortname⟧ でのカスタム指示の使用

カスタム指示を使用すると、コードを追加する場所、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供できます。すべてのプロンプトで繰り返すのではなく、このガイダンスをMarkdownファイルに保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている1つの規約から始めます。 [Agent Customizations エディター](⟦U75⟧) で指示を作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、設定については、[カスタム指示リファレンス](⟦U76⟧) を参照してください。

指示はモデルをガイドするものです。コンプライアンスを保証するものではなく、テスト、コードレビュー、セキュリティ制御の代わりにもなりません。入力時の [インラインサジェスチョン](⟦U77⟧) には適用されません。

## プロジェクトの指示の概要

リポジトリのルートを開き、使用する予定の [エージェントハーネスを選択](⟦U78⟧) します。ハーネスによって、どの指示ファイルが読み取られるかが決まります。たとえば、⟦L7:variables.product.prodname_copilot_short⟧ セッションで Claude モデルを選択しても、Claude ハーネスには切り替わりません。

最初のセットアップでは、テストセッションからコミットされていない指示にアクセスできるように、新しいワークツリーではなく現在のフォルダーで作業します。

### プロジェクトの指示を作成する

1. コマンドパレット (⟦I19⟧) から **Chat: Open Customizations** を実行して Agent Customizations エディターを開き、**Instructions** タブを選択します。

1. プロジェクトの指示ファイルを追加するには、**Workspace** の横にある ⟦I20⟧ を選択し、⟦I21⟧ や ⟦I22⟧ など、ハーネス用に提示されたプロジェクト指示ファイルを選択します。エディターによって、ワークスペースにファイルが作成されるか、ファイルが開きます。

   リポジトリにすでにプロジェクト指示ファイルがある場合は、競合するコピーを作成するのではなく、既存のファイルを開いてください。

1. 繰り返し発生する問題に対処するいくつかの具体的なルールを追加します。たとえば、Node.js APIプロジェクトでは、次の指示を使用できます。パスとテストコマンドを、リポジトリで機能するものに置き換えてください。

   ⟦C1⟧

1. ファイルを保存します。これらのプロジェクト指示ファイルには、フロントマターは必要ありません。

| ローカル ⟦I27⟧ | ⟦I28⟧ または ⟦I29⟧ |

### 指示を検証する

ルールが結果に影響するような小さなタスクをテストします。最初から最後まで同じハーネスとリポジトリを使用します。

1. コマンドパレット (⟦I31⟧) から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これは、エージェントがルールに従うかどうかではなく、検出されるかどうかを確認するものです。
1. 指示を作成した会話からのガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプトでルールを繰り返さずに、小さな変更を依頼します。APIの例では、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 利用可能な場合は、レスポンスの **References** セクションで指示ファイルを確認します。詳細が必要な場合は、[Agent デバッグログでリクエストを検査](⟦U80⟧) します。
1. 変更とツールのクエリを確認します。この例では、ハンドラーが追加された場所、データのアクセス方法、エージェントが関連するテストを実行したかどうかを確認します。

結果が目標を満たしている場合は、チームが使用できるように指示ファイルをレビューしてコミットします。満たしていない場合は、ルールを追加する前に、[ファイルが検出されたか、含まれていたか、従われたかを確認](⟦U81⟧) します。

完全な変更前後の比較とチームへのロールアウトワークフローについては、[コードベース向けのAI構成](⟦U82⟧) に従ってください。

## 指示の適用方法

スコープとアクティベーションは、異なる質問に対する答えです。スコープは、ガイダンスがどこで利用可能であり、誰がそれを共有するかを決定します。アクティベーションは、そのガイダンスがリクエストにいつ含まれるかを決定します。

| スコープ | 使用目的 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有されるプロジェクト規約 |
| ユーザー | ハーネスでサポートされている場所における、プロジェクト横断的な個人の好み |
| 組織 | サポートされているエクスペリエンス向けの一元管理されたガイダンス |

広く適用されるルールについては、プロジェクトの指示から始めます。コードベースの一部のみで必要なガイダンスについては、ターゲットを絞った指示を使用します。

| アクティベーション | 動作の仕組み |
|------------|--------------|
| プロジェクト全体 | ハーネスには、プロジェクト指示ファイルからのガイダンスが含まれます。 |
| ファイルパターン | ⟦I32⟧ ファイルは ⟦I33⟧ を使用するか、Claude ルールファイルは ⟦I34⟧ を使用して、エージェントが処理するファイルと一致させます。 |
| タスクの関連性 | ローカルセッションでは、⟦I35⟧ により、エージェントはタスク用の指示ファイルを読み込むかどうかを決定できます。これはパターンマッチングとは別です。 |
| 手動 | 自動検出またはアクティベーションが適切ではない特定のリクエストのガイダンスを添付します。 |

⟦I36⟧ などの指示ファイルは、既存のエージェントにガイダンスを提供します。[カスタムエージェント](⟦U83⟧) を定義するものではありません。コーディング規約やプロジェクトコンテキストではなく、再利用可能な多段階のワークフローについては、[エージェントスキル](⟦U84⟧) の使用を検討してください。自分でワークフローを作成する前に、[カスタマイズマーケットプレイスで既存のスキルを探して](⟦U85⟧) ください。リポジトリ固有のコマンドと規約は、プロジェクトの指示に記述してください。

### 1つのリクエストに指示を添付する

1回限りの要件については、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

1つのリクエストのために既存の指示ファイルを再利用するには、チャット入力の **Add Context** (⟦I68⟧ アイコン) を選択し、リクエストを送信する前にファイルを選択します。

## 効果的な指示の記述

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを記述します。

| 代わりに | 次のように記述します |
|------------|-------|
| 良いテストを記述する。 | ⟦I69⟧ のフィクスチャを再利用し、テストの変更後に ⟦I70⟧ を実行する。 |
| アーキテクチャに従う。 | HTTPハンドラーが独立してテスト可能な状態を維持できるように、データベースアクセスを ⟦I71⟧ に保持する。 |
| スタイルに従う。 | エラー文字列を返すのではなく、⟦I72⟧ の既存のエラー型を使用する。 |

* **ルールを簡潔に保つ。** 各要件に対して短いステートメントを使用し、自明ではない制約については説明します。
* **実行可能な詳細を優先する。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避ける。** フォーマッターやリンターによって強制されるルールを重複させないでください。特殊なガイダンスはプロジェクト全体のファイルから移動させます。
* **コードとともに指示をメンテナンスする。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを慎重に参照する。** 相対パスと ⟦I73⟧ 区切り文字を使用したMarkdownリンクを使用します。リンクは、ドキュメントの内容がモデルに到達することを保証するものではありません。[参照されたファイルの動作](⟦U88⟧) を確認してください。

### 競合する指示の解決

共有要件は、個人、リポジトリ、組織のガイダンス間で一貫性を保ちます。普遍的な優先順位に依存しないでください。[組み合わせのルールはハーネスによって異なり](⟦U89⟧) ます。

個人の指示が1つのライブラリを要求し、リポジトリが別のライブラリを要求している場合は、競合している個人のルールを削除するか、範囲を狭めます。補正するためにもう1つのルールを追加しないでください。競合を解決した後に、新しいチャットで同じ代表的なタスクを繰り返します。

## プロジェクトと個人の指示の管理

Agent Customizations エディターの **Instructions** に戻って、既存の指示を見つけて編集します。個人の指示を追加するには、**User** の横にある ⟦I74⟧ を選択します。ハーネスでサポートされている名前と保存場所のプロンプトに従い、ファイルを保存し、そのハーネスを使用した新しいチャットで検証します。

プロジェクト横断的な個人の好みには、ユーザーのスコープを使用します。チームが望んでいる場合を除き、個人の応答の好み共有プロジェクトファイルに配置しないでください。場所と同期の制限については、[ユーザー指示](⟦U90⟧) を参照してください。

また、関連するエージェント、スキル、またはツールとともに、[エージェントプラグイン](⟦U91⟧) 内のルールコンポーネントとして指示を配布することもできます。サポートは、選択したハーネスとプラグインの形式によって異なります。クライアント間でバンドルを共有する前に、[プラグインの互換性](⟦U92⟧) を確認してください。

## 指示のトラブルシューティング

ガイダンスを変更する前に、障害のステージを特定します。

| 観察される内容 | 確認すべき事項 |
|------------------|---------------|
| ファイルが Customizations エディターにリストされない。 | 選択したハーネス、ファイル名、サポートされている場所、およびセッションが変更を含むフォルダーを使用しているかどうかを確認します。 |
| ファイルが検出されたが、タスクに含まれない。 | フロントマターのエラーとアクティベーション条件を確認します。一致するファイルをテストするか、手動で指示を添付します。ローカルの場合は、該当する[検出設定](⟦U99⟧) を確認します。 |
| ファイルが含まれているが、結果がそれに従わない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返し、実際の変更とツールのクエリを比較します。 |

利用可能な場合のレスポンスの **References** セクションは、コンプライアンスではなく、包含の確認に役立ちます。詳細な証拠については、[指示の診断](⟦U100⟧) に従ってください。問題の再現の前にロギングを準備します。
