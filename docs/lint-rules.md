# リント規則（案）

訳文を、決定論的な静的検査で確かめるための規則の案です。採用する項目も、検出の厳しさも、未決です。リントの中身は、まだ決めていません。検査の実装は、この文書の対象外です。

この文書の作成日は2026年11月11日（Asia/Tokyo）です。規則の根拠は、[訳し方の指針と用語集（案）](translation-guidelines.md)の決定事項と、原文との照合です。意味の正しさや、日本語の自然さそのものは、ここには含めません。それらは人が見ます。詳しくは[翻訳モデルの選び方（案）](model-evaluation.md)を参照してください。

## 位置づけ

検査は、原文と訳文を比べるプログラム、または訳文だけを見る規則で判定します。LLMの判断には任せません。通らなかった箇所は、公開せず、差し戻すか、人の確認待ちにします。

ツールの候補は、次のとおりです。役割を分けて使う想定です。

| ツール                                                                                                                                                  | 向いていること                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| [textlint](https://github.com/textlint/textlint)                                                                                                        | 日本語の表記、文体、冗長な言い回し                                           |
| [textlint-rule-preset-ja-technical-writing](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing)                                   | 技術文書向けの既成ルール一式。後述するとおり、既定のままでは指針と衝突します |
| [textlint-rule-preset-ja-spacing](https://github.com/textlint-ja/textlint-rule-preset-ja-spacing)（と、その中の`ja-space-between-half-and-full-width`） | 和欧のあいだの空白                                                           |
| [prh](https://github.com/prh/prh) / [textlint-rule-prh](https://github.com/textlint-rule/textlint-rule-prh)                                             | 用語集と、禁止する訳語の置換検査                                             |
| [markdownlint](https://github.com/DavidAnson/markdownlint)                                                                                              | マークダウン単体の健全さ。原文との一致は見られません                         |
| 独自のスクリプト                                                                                                                                        | 原文と訳文の構造比較、Liquid、フロントマター、UIの書式、長さの比             |

コードブロックとインラインコード、残しているLiquid、URLの中は、日本語の表記規則の対象外にします。壊してはいけない箇所を、表記の規則で誤って直さないためです。

## 深刻度の目安

深刻度も案です。公開してよいかの線引きは、あとで決めます。

- **error。** 通らなければ、そのページは公開しません。原文との構造の食い違い、Liquidの破損、リンク切れ、読めないフロントマター、制御文字や置換文字の混入などです。
- **warning。** 直すべきですが、文脈を見て人が判断してよいものです。表記の揺れ、用語集との不一致のうち、一般の意味か固有名詞かで分かれうるものなどです。

試し訳の段階では、errorもwarningも件数を集計し、モデルの採点表に載せます。本番の「合格」の定義は、その後に決めます。

## 訳し方の決定事項から導く規則

各規則に、検査の内容、例、深刻度の案、候補のツールを付けます。例の「避けたい形」は、訳文に出してはいけない形です。

### 1.本文を敬体で揃える

- **検査。** 本文と手順の文末が、です・ます調であること。「だ。」「である。」「だった。」など、である調の言い切りが残っていないこと。見出し、表の項目、図のキャプションの体言止めは、対象外にします。
- **例。** 避けたい形:「リポジトリを作成する。」「設定は次のとおりである。」望ましい形:「リポジトリを作成します。」「設定は次のとおりです。」
- **深刻度（案）。** error。文体は決定事項です。ただし、体言止めの除外を誤ると、見出しが大量に引っかかります。除外の精度が足りないあいだは、warningでもよいです。
- **候補のツール。** textlintの`no-mix-dearu-desumasu`。既定は、本文をですます、箇条書きをである、にします。本プロジェクトでは、手順のリストもですますに揃える必要があります。使うなら、`preferInList`を「ですます」へ変えます。

### 2.製品名とUIの文言を、英語のまま残す

- **検査。** 用語集で「英語のまま」と決めた語（Agents window、Command Palette、Copilot cloud agent、GitHub Copilot、Visual Studio Codeなど）が、日本語へ置き換わっていないこと。
- **例。** 避けたい形:「エージェントウィンドウを開きます。」「コマンドパレットを使います。」望ましい形:「Agents windowを開きます。」「Command Paletteを使います。」
- **深刻度（案）。** error（決まった語の誤訳）。用語集にまだ載っていない語は、warningに留め、用語集へ足す材料にします。
- **候補のツール。** prh（禁止する日本語形を列挙する）。独自スクリプトで、原文に出た製品名・UIを訳文でも英語のまま追跡してもよいです。

### 3. UIの書式を、原文のままにする

- **検査。** 原文が太字なら訳文も太字であること。原文が太字でなければ、訳文で太字を足していないこと。訳の側で、角括弧を独自に足していないこと。
- **例。** 原文が`Select **Settings**.`なら、`**Settings**を選択します。`はよく、`[Settings]を選択します。`は避けます。原文が`Open the Command Palette.`なら、`Command Paletteを開きます。`はよく、`**Command Palette**を開きます。`は避けます。
- **深刻度（案）。** error。書式を足したり外したりすると、画面上の名前かどうかが、読者に伝わりにくくなります。
- **候補のツール。** 独自スクリプト。原文と訳文のMarkdown ASTを比べ、強調とリンク、インラインコードの位置を、UI語ごとに見ます。textlintやmarkdownlintだけでは、原文との対応は取れません。

### 4. pull requestとissueを、英語のまま残す

- **検査。** 「プルリクエスト」「プル・リクエスト」「イシュー」「課題」などへ置き換えていないこと。UIのIssuesや、ボタン名のPull requestsも、英語のままであること。
- **例。** 避けたい形:「プルリクエストを作成します。」「課題を開きます。」望ましい形:「pull requestを作成します。」「issueを開きます。」
- **深刻度（案）。** error。ただし「課題」は、一般の日本語として妥当な文もありえます。機械が「課題」をすべて弾くと、誤検知が出ます。最初は「プルリクエスト」「イシュー」だけをerrorにし、「課題」はwarningとする案もあります。
- **候補のツール。** prh。

### 5.日本語と英数字のあいだに、空白を入れない

- **検査。** 和文と半角の英数字が隣り合うとき、そのあいだに空白が無いこと。リンクの閉じ括弧のあとと、#123のような参照番号のあとは、空白を許します。
- **例。** 避けたい形:「Settingsを選択します。」「VS Codeの設定。」望ましい形:「Settingsを選択します。」「VS Codeの設定。」
- **深刻度（案）。** error。規則は決まっています。検出そのものは機械向きです。
- **候補のツール。** textlint-rule-ja-space-between-half-and-full-width。`space`を`never`にします。リンク閉じの直後など、許す箇所は、規則のオプションか、独自の例外で扱います。既定のまま使うと、Microsoft流（空白を入れる）と逆になりますので、設定の確認が必要です。

### 6.英語のUI名に、日本語を補わない

- **検査。** `Command Palette（コマンドパレット）`のように、英語のUI名や製品名の直後へ、日本語の併記を足していないこと。
- **例。** 避けたい形:「Command Palette（コマンドパレット）を開きます。」望ましい形:「Command Paletteを開きます。」
- **深刻度（案）。** error。
- **候補のツール。** 独自のtextlint規則、または正規表現によるスクリプト。用語集に載った英語名の直後にある、全角括弧とその中の日本語を検出します。略語の正当な展開（「Model Context Protocol（MCP）」や、「継続的インテグレーション（CI）」）は、除外する必要があります。

### 7.数字と単位を、詰めて書く

- **検査。** 数字と単位のあいだに空白が無いこと。単位は半角です。
- **例。** 避けたい形:「10 GB」「3 ms」「80 %」。望ましい形:「10GB」「3ms」「80%」。
- **深刻度（案）。** error。
- **候補のツール。** 独自のtextlint規則、または正規表現。対象の単位は、GB、MB、KB、GiB、MiB、ms、秒を表すs、%など、よく出るものから列挙します。バージョン番号（1.146）や、日付、ポート番号は、対象外です。

### 8.カタカナの複合語を、空白で区切らない

- **検査。** 「アクセス トークン」「ダイアログ ボックス」のように、カタカナ語のあいだを空白で区切っていないこと。
- **例。** 避けたい形:「アクセス トークンを発行します。」望ましい形:「アクセストークンを発行します。」
- **深刻度（案）。** error。
- **候補のツール。** prhに、区切った形と、詰めた形の対を載せる。textlint-rule-ja-no-space-between-full-widthは、全角文字どうしの空白を広く検出しますが、例外の扱いを確認してから使います。

### 9.カタカナの長音を、Microsoft流に揃える

- **検査。** サーバー、ユーザー、フォルダー、コンピューター、エディター、デバッガーなど、語末の長音を付ける語が、短くなっていないこと。プロセッサ、プログラマ、コンパイラ、コネクタ、レジスタなど、例外表の語が、長音付きになっていないこと。
- **例。** 避けたい形:「サーバを起動します。」「プロセッサーを選びます。」望ましい形:「サーバーを起動します。」「プロセッサを選びます。」
- **深刻度（案）。** error。対は辞書で決まるため、機械向きです。新しい語が出たら、用語集を先に直し、辞書をそれに合わせます。
- **候補のツール。** prh。指針の例外表と、用語集を、同じ対訳表の入力にします。

### 10.禁止しやすい翻訳調と、禁止する訳語

- **検査。** 「〜することができます」「〜することが可能です」「あなたは」「弊社」が、本文に出ていないこと。用語集が禁じる形（「レポジトリ」など）が無いこと。全角の英数字（Ａ、１など）が無いこと。和文の途中に、カンマ「,」やピリオド「.」、em dash（—）が混じっていないこと。
- **例。** 避けたい形:「あなたは設定を変更することができます。」「これは便利です—設定から使えます。」望ましい形:「設定を変更できます。」「これは便利な機能です。設定から使えます。」
- **深刻度（案）。** 「〜ことができます」「あなたは」「弊社」、全角英数字、和文中のカンマ・ピリオド、em dashはerror。「利用する」「使用する」の多用など、まだ指針が案のものは、採否ごと未決です。
- **候補のツール。** textlint-rule-ja-no-redundant-expression（「することができる」を「できる」へ近づける）。prh。全角英数字とダッシュは、独自規則か正規表現。英語の製品名、コード、URLの中のピリオドとカンマは、対象外にします。

### 11.機能名と、一般の意味の見分け

- **検査。** 完全な自動判定には向きません。できるのは、用語集で「英語のまま」と決まった形が消えていないことと、「文脈次第」の語について、両方の形の出現を記録することです。organizationを「組織」と訳した箇所が妥当かどうかは、人が見ます。
- **例。** 「custom instructionsを設定します。」は機能名としてよいです。「自分で書いた指示を渡します。」は、一般の意味としてよいです。どちらに取るか迷う箇所は、リントではwarningに留めます。
- **深刻度（案）。** 決まった誤訳（機能名を訳してしまったことが明らかな場合）はerror。文脈次第の語はwarning。
- **候補のツール。** prhと、独自スクリプトによる出現位置の一覧。最終判断は人です。

手順の文末（「〜します」と「〜してください」の使い分け）も、同様に、完全な自動判定には向きません。注意書きの枠（`> [!NOTE]`、`> [!IMPORTANT]`、`> [!WARNING]`など）の中だけ「してください」を許す、といった粗い検査はできます。枠の外の注意文までは、人が見ます。

## 原文との照合

こちらは、訳し方ではなく、原文を壊していないかの検査です。翻訳方法の文書にも、同じ趣旨の項目があります。こちらでは、規則の形に落として書きます。深刻度は、いずれもerrorの案です。候補のツールは、いずれも独自のスクリプトです。Markdownの解析には、remarkやmdastを使える見込みです。markdownlintは、訳文単体の壊れは見つけられますが、原文との一致は見られません。

### 12. Markdownの構造

- **検査。** 見出しの数とレベル、リストの項目数と入れ子、表の行数と列数、コードフェンスの開閉、注意書き（`> [!NOTE]`など）の種類が、原文と一致すること。
- **例。** 原文が3列の表なのに、訳文でパイプが足りず2列になる。原文の手順リストが、訳文で段落に潰れる。

### 13.リンクと画像

- **検査。** リンク先のURLと、画像のパスが原文と一致すること。リンクテキストだけが訳されていること。内部リンクが解決できること。アンカーが存在すること。`AUTOTITLE`の構文が、残しているなら原文どおりであること。
- **例。** 画像パスの拡張子が変わる。内部リンクのアンカーだけが、訳文側で消える。

### 14.コードブロック

- **検査。** フェンスの開閉、言語指定、中身が原文と一致すること。インラインコードの個数と中身も、原則として一致すること。コードのコメントを訳すかどうかは、方針がまだ無いため、最初は中身を変えない案にします。
- **例。** フェンスが閉じられず、あとの本文がコード扱いになる。インラインコードの中のコマンドが、日本語に置き換わる。

### 15. Liquidタグ

- **検査。** タグの数、種類、順序、中身が原文と一致すること。`{%-`のような空白制御も一致すること。`ifversion`の開閉が対応すること。`{% data %}`の参照パスが変わっていないこと。
- **例。** `{%- ifversion ghes %}`のハイフンが落ちる。`{% data reusables.foo %}`のパスが書き換わる。`endif`が消える。

### 16.フロントマターと、翻訳元の記録

- **検査。** YAMLとして読めること。原文から引き継ぐキーの集合が同じこと。訳してよいキー（`title`、`shortTitle`、`intro`、`MetaDescription`など）以外の値が、原文から変わっていないこと。訳文側で足す`source.repo`、`source.path`、`source.commit`、`translated`が、欠けていないこと。
- **例。** `versions`や`ContentId`が欠ける。`source.commit`が空のまま公開される。YAMLの引用符が壊れ、フロントマターとして読めない。

### 17.訳抜けの形跡

- **検査。** 用語集とコード、残している英語の固有名詞を除き、英語の文がそのまま残っていないこと。原文に対する訳文の長さの比が、想定の範囲に収まっていること。範囲の数字自体は未決です。翻訳方法の文書では、文字数比0.4〜1.2を例として挙げています。
- **例。** 段落の後半が英語のまま残る。短い見出しだけ訳され、本文が空に近い。
- **深刻度（案）。** 英語の文の残留はerror。長さの比は、誤検知が出やすいので、最初はwarningの案です。

## 既存のツールと、そのまま使うときの注意

textlint-rule-preset-ja-technical-writingは、技術文書向けの既成ルールとして有力です。ただし、既定のまま採用すると、指針と衝突します。少なくとも次は、設定を変えるか、外す必要があります。

| 既定                                                          | 指針との関係                                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 箇条書きはである調（`no-mix-dearu-desumasu`）                 | 手順のリストも、ですますに揃えます                                                         |
| 感嘆符と疑問符を使わない（`no-exclamation-question-mark`）    | 原文に明らかな問いかけや注意があるときは、全角の「？」や「！」を許します                   |
| 弱い表現を使わない（`ja-no-weak-phrase`）                     | 原文が推量や可能性を述べているときの「でしょう」「かもしれません」は、指針で許しています   |
| 1文は100文字以下、読点は1文に3つまで、連続する漢字は6文字まで | 製品名の長い文や、固有の漢語で、すぐ例外が出ます。採用するなら、閾値と例外の列挙が必要です |

一方、次は指針と向きが揃っています。候補として残りやすいです。

- `ja-no-redundant-expression`（「することができる」を「できる」へ）
- `ja-no-mixed-period`（和文の句点は「。」）
- `no-hankaku-kana`（半角カナを使わない）
- `no-invalid-control-character`、`no-zero-width-spaces`、`no-nfd`（制御文字や、分解された濁点）
- `ja-unnatural-alphabet`（IMEの打ち間違い）
- `no-unmatched-pair`（括弧の対応）
- `arabic-kanji-numbers`（数は算用数字、慣用は漢数字）

preset-ja-spacingは、和欧空白の規則を、`space: "never"`に変えて使う案です。既定値を確認せずに入れると、空白を入れる側の規則になることがあります。

prhの辞書は、指針の用語集と、長音の例外表を正本にします。辞書だけが先に変わって、用語集とずれる状態は避けます。

## 未決事項

1. **リントの中身そのもの。** この文書の規則を、どれ採用し、どれを見送り、どれをerrorにするか。
2. **textlintのプリセットを、どこまで使うか。** 既定のまま使わないことだけは、上に書いたとおりです。
3. **長さの比など、閾値を伴う規則の数字。**
4. **「課題」や、文脈次第の語を、どこまで機械で弾くか。**
5. **三点リーダーを「...」と「…」のどちらに揃えるか。** 揃える対象が決まれば、リントに載せられます。いまは指針でも未決です。

この文書は規則の案であり、上記が決まるまでは、何も採用しません。
