## 決定と案の区別

いま**決定**しているのは、次の6点です。本文では「決定」と明示します。

それ以外は、すべて**案**または**検討中**です。採用するかどうかは、これから決めていただきます。決定していないことを、決まったこととしては書きません。

## 決定事項

1. **文体は敬体（です・ます調）にします。** 解説も手順も、です・ますで統一します。である調や、だ・であるで言い切る文は使いません。見出しや表の項目、図のキャプションは体言止めにしてかまいません。
2. **製品名とUIの文言は、英語のまま残します。** 例は、Agents window、Copilot cloud agent、Command Palette、pull requestなど、画面上の表示名です。GitHub、GitHub Copilot、Visual Studio Code、VS Codeのような製品名も、英語のままにします。
3. **手順の文末は「〜します」を基本とし、注意や必須の操作だけ「〜してください」とします。**
4. **カタカナの長音は、Microsoftの日本語スタイルガイドに倣います。** サーバー、ユーザー、フォルダーなど、語末の長音を付けることと、同ガイドの例外（プロセッサ、プログラマなど）の両方に従います。
5. **UIの文言は、原文の書式のままにします。** 原文が太字なら太字を保ち、太字でなければ太字を足しません。角括弧や太字を、訳の側で独自に足しません。
6. **概念としてのpull requestとissueも、英語のままにします。** 「プルリクエスト」「イシュー」「課題」などにはしません。

## 基本的な文体

文末、手順と指示の言い方、カタカナの長音は決定です。それ以外の項目は、ことわりが無い限り案です。

### 文末

本文の文末は、です・ます調に揃えます（決定）。「です」「ます」「ません」「でした」「ました」を基本にします。

「でしょう」「かもしれません」は、原文が推量や可能性を述べているときに限ります。原文が断定している箇所を、訳の都合で弱めません。見出しを「〜とは」「〜の概要」のように体言止めにすることは、問題ありません。

### 手順と指示の言い方

How-toやクイックスタートの手順は、**「〜します」を基本とします（決定）。** 注意や必須の操作だけ「〜してください」とします。ドキュメントらしい落ち着いた調子になり、です・ます調とも自然につながります。

| 原文の趣旨 | 訳し方（決定） | 例 |
| --- | --- | --- |
| 手順の操作 | 〜します | ファイルを開きます。原文が**Settings**なら、**Settings**を選択します。 |
| 必須の注意、警告、お願い | 〜してください | 変更を保存してから進めてください。トークンを共有しないでください。 |
| できることの説明 | 〜できます | ブランチを切り替えて比較できます。 |

Microsoftの日本語スタイルガイドでは、操作を促す文に「〜してください」を使う、と定めています。一方で、同ガイドの例には「ファイルを開きます」もあります。本プロジェクトでは、手順の基本を「〜します」にし、読者への注意や必須の操作だけ「〜してください」とします。

「してください」をすべての手順に使うと、指図が続いているように聞こえることがあります。逆に、注意文まで「します」にすると、必要性が伝わりにくくなります。

### 翻訳調を避ける

英語の構造をそのまま写すと、意味は通っても日本語として不自然になります。次を避けます。

**不要な人称です。** 「you」「we」「I」は、多くの場合、主語を立てずに訳します。「あなたは設定を開くことができます」とはしません。「設定を開けます」とします。主語が必要なときは、対象を具体的にします（「管理者は」「この拡張機能は」）。「弊社」は使いません。

**受身の濫用です。** 読者が行う操作を、英語の受身のまま「〜されます」とはしません。「A repository is created」という手順は、「リポジトリが作成されます」より「リポジトリを作成します」が自然です。一方、システム側が自動で行う動きは、受身が自然です。「ダイアログが表示されます」「コンピューターが再起動されます」。

**「〜することができます」です。** 許可や可能な操作は、原則として「〜できます」にします。「設定を変更することができます」ではなく、「設定を変更できます」。原文のcanやyou can、be able toを、毎回「ことができます」にはしません。

そのほか、次のような翻訳調も避けます。

- 「〜することが可能です」→「〜できます」
- 「〜ということになります」→必要なとき以外は省きます
- 「〜に対して」「〜に関して」の連発→「〜の」「〜を」「〜では」など、助詞で足りる形にします
- 「利用する」「使用する」の多用→「使う」「開く」「選ぶ」など、具体的な動詞を優先します
- 原文の語順を守るための「それは」「このことは」の残留

目指すのは、原文の意味を落とさず、初めから日本語で書かれたように読める文です。

### 句読点

和文の句点は「。」、読点は「、」を使います。和文の途中でカンマ「,」やピリオド「.」は使いません。英語の製品名、識別子、コード、URLの中は、原文どおりです。

引用や強調の括りは、次を提案します。

- 日本語の語句や、文書・節の題名は「」
- UIの文言は、原文の書式のまま残します（後述）。原文が太字なら太字にし、太字でなければ足しません
- コード、コマンド、ファイル名、識別子は、原文どおりインラインコードにする

疑問符「？」や感嘆符「！」は、原文に明らかな問いかけや注意があるときに限り、全角で使います。解説文の末尾を「？」で終えず、平叙文にすることを優先します。三点リーダーは「...」または「…」のどちらかに揃えます。どちらに揃えるかは未決です。

### 全角と半角、和欧のあいだの空白

次を提案します。

- 和文の句読点と、和文を囲む括弧は全角です
- 英数字、単位、製品名、UIの文言、コードは半角です
- カタカナは全角です
- 全角の英数字（Ａ、１など）は使いません
- **日本語と英数字のあいだに空白を入れません。** 「Settingsを選択します」「VS Codeの設定」「3つのファイル」のように続けます。リンクの閉じ括弧のあとや、#123のような参照番号のあとに空白を置くのは、構いません

この空白の置き方は、Microsoftの日本語スタイルガイド（全角と半角のあいだに半角空白を入れる）とは異なります。本プロジェクトのこれまでの文書の書き方に合わせる案です。まだ決定ではありません。

カタカナの複合語を「ダイアログボックス」と続けるか、「ダイアログ ボックス」と区切るかも、未決です。Microsoftのガイドは区切る方針です。こちらは、短い語は続け、長い複合だけ区切る、といった中間も考えられます。決めるまでは、用語集に載った語の形を優先することを提案します。

### 数字と単位

- 数は半角の算用数字にします。「1つ」「3個」「10回」です。「一つ」「３個」にはしません
- 固有の言い回しや、数字に置き換えられない語は漢数字でもかまいません（「一部の機能」「第一章」に相当する慣用など）
- バージョン番号、日付のISO表記、ポート番号、コミットの短縮形は原文どおりです（1.146、2026-11-11、`7c3387d`）
- 本文中の日付は、「2026年11月11日」のように和暦にせず、西暦の日本語表記にします
- 単位は半角です。数字と単位のあいだは空けない案とします（10MB、3ms、80%）。Microsoftのガイドは、%以外の単位の前に空白を置きます。どちらにするかは未決です

### カタカナの長音

**Microsoftの日本語スタイルガイドに倣います（決定）。** サーバー、ユーザーなどの長音と、同ガイドの例外の両方に従います。

同ガイドは、平成3年6月28日内閣告示第2号「外来語の表記」を一次の典拠とし、次のように定めています。

- 英語の語末が-er、-or、-arに当たるものは、原則として長音符号「ー」を付けます。例: コンピューター、オペレーター、サーバー、ユーザー、フォルダー、ランナー、エディター、デバッガー
- それ以外は、長音を1字と数えて4字未満なら長音を付け、4字以上なら付けません。ただし促音「ッ」、拗音「ャュョ」、小さな「ァィゥ」は数えません。例: メニュー、キュー。一方、メモリ、プロシージャ
- 接頭辞と語幹は分けて考えます。例: プレビュー、インターフェイス
- 慣用による例外があります。例: プロセッサ、プログラマ、コンパイラ、コネクタ、レジスタ

「サーバ」「ユーザ」「フォルダ」のような、長音を省いた形は使いません。例外表に載っている語（プロセッサ、プログラマなど）は、例外に従います。用語集と食い違う語が出たら、用語集を先に直し、訳文をそれに合わせます。

### 括弧

- 和文の補足には全角の（）を使います。例: 敬体（です・ます調）
- 英語の製品名、UIの文言、識別子だけを括るときは、半角の()でもかまいません。ただし、UIは原文の書式のまま残し、括弧で重ねて囲みすぎないようにします
- 角括弧[]を、訳の側で独自に足しません。原文が角括弧を使っていれば、それに従います。Microsoftのガイドは[OK]のように角括弧を使いますが、こちらは原文の書式を優先します（決定）
- 入れ子になるときは、外側を（）、内側を「」にするか、文を分けます

### ダッシュの多用を避ける

英語のem dash（—）やen dash（–）を、和文にそのまま持ち込みません。PLaMoをはじめ、いくつかのモデルが、説明のつなぎにダッシュを多用することが知られています。和文では、読点、括弧、または文の分割で足りることがほとんどです。

| 避けたい形 | 代わりの例 |
| --- | --- |
| これは便利な機能です—設定から使えます。 | これは便利な機能です。設定から使えます。 |
| エージェント—クラウド上で動くもの—を使います。 | クラウド上で動くエージェントを使います。 |

範囲を示すハイフンや、識別子の中のハイフン（GPT-6.1、v1-146、ci-cd）は、原文どおり残します。和文のダッシュ「――」も、原則として使いません。

## 製品名・UIの文言と、一般用語の見分け方

製品名とUIの文言を英語のまま残すこと、概念としてのpull requestとissueも英語のままにすること、UIの文言を原文の書式のままにすること（原文が太字なら太字、そうでなければ足さないこと）は、決定です。何をUIや製品名と見なすかの細部は、案です。

### 見分け方の目安

**英語のまま残すもの（決定の範囲）**

- 製品名、プラン名、機能の正式名称。例: GitHub、GitHub Copilot、GitHub Actions、GitHub Codespaces、Visual Studio Code、VS Code、IntelliSense、Copilot cloud agent
- 画面に出る表示名。ウィンドウ、ビュー、タブ、ボタン、メニュー、コマンド、設定項目のラベルです。例: Agents window、Chat view、Command Palette、Settings、Pull requests、New issue
- 原文がUIを指して太字やコードにしてある語は、原則としてUIと見なします

**訳すもの**

- 一般概念、普通名詞、操作の説明。例: repository→リポジトリ、extension→拡張機能、settings（一般の「設定」）、agent（一般の「エージェント」）、prompt→プロンプト
- 同じ英語でも、UIを指していないときは訳します。「Open Settings」はUI、「change the extension settings」は「拡張機能の設定を変更します」

迷ったら、次で判断することを提案します。

1. その語を画面で探せる表示名として読者が使うか。使うなら英語のままです
2. 製品の固有名か、一般の技術用語か。固有名なら英語のままです
3. どちらにも取れるときは、その文では英語のまま残し、用語集の「扱い」と「メモ」を後で更新します。勝手に新しい訳語を増やしません

### 和文の中での書き方

UIの文言は、英語のまま置き、助詞を直につなぎます。**書式は原文に合わせます（決定）。** 原文が太字なら太字を保ち、太字でなければ太字を足しません。角括弧や太字を、訳の側で独自に足しません。日本語と英語のあいだに空白を入れないことは、まだ案です。

| 原文の例 | 訳の例 | 説明 |
| --- | --- | --- |
| Select **Settings**. | **Settings**を選択します。 | 原文が太字なので、太字のまま残します |
| Open the Command Palette. | Command Paletteを開きます。 | 原文が太字でないので、太字を足しません。画面の名前なので訳しません |
| Use the Agents window to start a session. | セッションを始めるには、Agents windowを使います。 | ウィンドウ名を「エージェントウィンドウ」とは訳しません |
| Start a Copilot cloud agent session. | Copilot cloud agentのセッションを開始します。 | 機能名は英語のまま、周辺の語だけ訳します |
| Create a pull request. | pull requestを作成します。 | UIも概念も英語のままです（決定） |
| Install an extension. | 拡張機能をインストールします。 | 一般概念なので訳します |
| Open the **Extensions** view. | **Extensions**ビューを開きます。 | 原文が太字のビュー名は、太字のまま残します。一般の「ビュー」は訳してよいとします |

原文が太字にしていない画面名（Command Palette、Agents windowなど）に、太字を足しません。

UI名のあとに日本語の説明を補う案もあります。例: Command Palette（コマンドパレット）。ただし、決定は「英語のまま残す」ことなので、補うかどうかは別途確認したい事項です。読者の製品UIが日本語になっていると、画面の表示と文書の英語名が一致しない、という問題があります。

## 略語と、ページ内で定義される用語（案）

文だけ、あるいは段落だけを訳すと、そのページで定義された略語が、別の意味に置き換わることがあります。本プロジェクトでも、同じ失敗を避ける必要があります。

次を提案します。

1. **略語は、原則として英語のまま残します。** API、CLI、IDE、URL、PR、MCP、PAT、SSH、YAMLなど、開発者に定着しているものは訳しません。無理に「アプリケーションプログラミングインターフェイス」のようにはしません
2. **初出で展開されている略語は、訳文でも同じ位置で展開します。** 原文が「Model Context Protocol (MCP)」なら、「Model Context Protocol（MCP）」とします。展開部に一般語が含まれるときだけ、その部分を訳します。例: continuous integration (CI)→継続的インテグレーション（CI）
3. **一度定めた略語は、そのページの終わりまで同じ形で使います。** 途中から別の訳や、別の展開に変えません。原文があとの文で略語だけを使っているなら、訳文も略語だけを使います
4. **ページ内の独自の定義を、一般的な意味で上書きしません。** ある記事が「runner」を特定の意味で定義しているなら、その定義を尊重します。用語集の一般訳と衝突するときは、ページ内の定義を優先し、必要なら用語集のメモに残します
5. **訳す単位は、少なくとも1ファイル（1ページ）の文脈を保ちます。** 文単位だけで略語を訳しません。定義が別ファイル（再利用片や用語集）にあるときは、その定義も一緒に渡します

PRはpull requestの略として広く使われます。UIの文言がPull requestである以上、本文で「PR」と略すかどうかは、原文に合わせることを提案します。原文がpull requestと書いている箇所を、勝手にPRへ縮めません。

## のちにリントへ回せそうな項目（候補）

リントの中身は未決です。ここでは、決定論的に検出できそうな候補だけを挙げます。採用する項目も、検出の厳しさも、まだ決めません。意味の正しさや、日本語の自然さそのものは、プログラムだけでは判定できません。

候補は次のとおりです。

- である調の残存（「だ。」「である。」「だった。」など。見出しや表の体言止めは除外する必要があります）
- 禁止しやすい表現（「〜することができます」「〜することが可能です」「あなたは」「弊社」）
- 日本語と英数字のあいだの空白（採用する場合）
- 全角英数字
- 和文に混じったカンマ・ピリオドや、em dash（—）
- 長音の揺れ（サーバ／サーバー、ユーザ／ユーザー、フォルダ／フォルダーなど）
- 用語集との対応（原文に出た語が、指定の訳語または「英語のまま」の形で訳文にあること、禁止訳語が無いこと）
- 製品名・UIの誤訳（Agents windowを「エージェントウィンドウ」にする、Command Paletteを「コマンドパレット」にする、pull requestを「プルリクエスト」にする、など）
- UIの書式が原文と食い違うこと（原文に無い太字や角括弧を足す、原文の太字を外す、など）

書式の保全（マークダウンやLiquidを壊していないか）は、翻訳方法の文書側の話なので、ここでは扱いません。

## 確認したいこと

決定済みの事項以外で、特に確認したいことは次のとおりです。

1. **日本語と英数字のあいだに空白を入れない案でよいですか。** Microsoftのガイドとは異なります
2. **読者の製品UIが日本語のとき、英語名をどう補いますか。** 補わず英語のままにする、初出だけ日本語名を括弧で添える、といった案が考えられます
3. **Organization、Enterprise、Team、upstream、codespace、Agent mode、custom instructionsは、英語のまま残す範囲をどこまでにしますか**
4. **数字と単位のあいだを空けるか、カタカナ複合語（ダイアログボックス）を空白で区切るか**も、まだ決めていません

これらが決まれば、この文書の該当箇所を「決定」に更新し、用語集の「扱い」を整えます。
