# ⟦BKVW⟧ でカスタム指示を使用する

カスタム指示は、コードの追加先、使用するライブラリ、実行するテストなど、プロジェクトに関する再利用可能なガイダンスをエージェントに提供します。このガイダンスをすべてのプロンプトで繰り返すのではなく、Markdownファイルに保存し、ソース管理を通じてプロジェクトの指示を共有します。

エージェントが繰り返し見落としている1つの規約から始めます。[Agent Customizations editor](⟦27M8⟧)で指示を作成し、よりターゲットを絞ったガイダンスを追加する前に、新しいチャットでその効果をテストします。サポートされている場所、ファイルの構文、設定については、[Custom instructions reference](⟦8G6T⟧)を参照してください。

指示はモデルをガイドするものです。コンプライアンスを保証するものではなく、テスト、コードレビュー、セキュリティ制御の代わりにもなりません。入力時の[inline suggestions](⟦J574⟧)には適用されません。

## プロジェクトの指示を開始する

リポジトリのルートを開き、使用する予定の[select the agent harness](⟦NCSE⟧)を選択します。ハーネスによって、どの指示ファイルが読み込まれるかが決まります。たとえば、⟦GZ4H⟧ セッションで Claude モデルを選択しても、Claude ハーネスに切り替わるわけではありません。

最初のセットアップでは、コミットされていない指示にテストセッションからアクセスできるようにするため、新しいワークツリーではなく現在のフォルダで作業します。

### プロジェクトの指示を作成する

1. コマンドパレット（⟦R8BD⟧）から **Chat: Open Customizations** を実行して Agent Customizations エディタを開き、**Instructions** タブを選択します。

1. プロジェクト指示ファイルを追加するには、**Workspace** の横にある ⟦XRG8⟧ を選択し、⟦KXWS⟧ や ⟦7233⟧ など、お使いのハーネス向けに提示されたプロジェクト指示ファイルを選択します。エディタがワークスペース内でファイルを作成または開きます。

   リポジトリにすでにプロジェクト指示ファイルが存在する場合は、競合するコピーを作成せずにそちらを開いてください。

1. 繰り返されている問題に対処する具体的なルールをいくつか追加します。たとえば、Node.js の API プロジェクトでは次のような指示を使用できます。パスとテストコマンドは、お使いのリポジトリで動作するものに置き換えてください。

   ⟦P444⟧

1. ファイルを保存します。これらのプロジェクト指示ファイルにフロントマターは必要ありません。

#### ファイルを直接作成する

Agent Customizations エディタ外でファイルを作成したい場合は、お使いのハーネスでサポートされているプロジェクト指示ファイルを使用してください。以下のパスはリポジトリのルートからの相対パスです。必要に応じて存在しないフォルダを作成してください。

| ハーネス | プロジェクト指示ファイル |
|---------|---------------------------|
| ⟦MYKH⟧ | ⟦VM5E⟧ または ⟦7GRZ⟧ |
| ⟦624K⟧ | ⟦R4BF⟧ |
| ⟦ZWWV⟧ | ⟦RBXC⟧ |
| Local ⟦BEHF⟧ | ⟦VADV⟧ または ⟦2V6Y⟧ |

ルールを追加してファイルを保存し、後述の手順に従って検証します。⟦K4FQ⟧ は Codex 専用のファイルではなく、エージェント横断的なフォーマットです。1つのファイルを複数のハーネス間で共有する前に、[supported formats](⟦R8ZE⟧)を参照してください。

### 指示を検証する

ルールが結果に影響するような小さなタスクをテストします。最初から最後まで同じハーネスとリポジトリを使用します。

1. コマンドパレット（⟦73N9⟧）から **Chat: Open Customizations** を実行します。**Instructions** を選択し、ファイルがリストされていることを確認します。これは、エージェントがルールに従っているかどうかではなく、検出されるかどうかを確認するものです。
1. 指示を作成した会話からのガイダンスにテストが依存しないように、新しいチャットを開始します。
1. プロンプトでルールを繰り返さずに、小さな変更を依頼します。API の例であれば、プロジェクトの既存のパターンを使用してエンドポイントを追加するようにエージェントに依頼します。
1. 可能であれば、応答の **References** セクションで指示ファイルを確認します。詳細が必要な場合は、[inspect the request in Agent Debug Logs](⟦RKPK⟧)を参照してください。
1. 変更内容とツールの動作を確認します。例の場合は、ハンドラーがどこに追加されたか、データにどのようにアクセスしているか、エージェントが関連するテストを実行したかを確認します。

結果が目的に合致している場合は、チームが使用できるように指示ファイルをレビューしてコミットします。そうでない場合は、ルールを追加する前に[identify whether the file was discovered, included, or followed](⟦9G9X⟧)を確認してください。

変更前後の完全な比較とチームへの導入ワークフローについては、[Configure AI for your codebase](⟦3BJW⟧)に従ってください。

## 指示の適用方法

スコープとアクティベーション（有効化）は、それぞれ異なる疑問に答えるものです。スコープは、ガイダンスがどこで利用可能か、誰がそれを共有するかを決定します。アクティベーションは、そのガイダンスがリクエストにいつ含まれるかを決定します。

| スコープ | 用途 |
|-------|------------|
| ワークスペースまたはリポジトリ | ソース管理を通じてコントリビューターと共有するプロジェクト規約 |
| ユーザー | ハーネスがサポートする場所における、プロジェクトをまたいだ個人的な好み |
| 組織 | サポートされているエクスペリエンス向けの一元管理されたガイダンス |

広範囲に適用されるルールについては、プロジェクトの指示から始めます。コードベースの一部のみで必要なガイダンスには、ターゲットを絞った指示を使用します。

| アクティベーション | 仕組み |
|------------|--------------|
| プロジェクト全体 | ハーネスはプロジェクト指示ファイルからのガイダンスをインクルードします。 |
| ファイルパターン | ⟦4KGE⟧ ファイルは ⟦XJDK⟧ を使用し、Claude ルールファイルは ⟦4HHQ⟧ を使用して、エージェントが作業するファイルに一致させます。 |
| タスクの関連性 | Local セッションでは、⟦K5JS⟧ により、エージェントがタスク用の指示ファイルを読み込むかどうかを判断できます。これはパターンマッチングとは別個のものです。 |
| 手動 | 自動検出やアクティベーションが適切ではない特定のリクエストにガイダンスを添付します。 |

⟦YB7F⟧ のような指示ファイルは、既存のエージェントにガイダンスを提供します。[custom agent](⟦QHCH⟧)を定義するものではありません。コーディング規約やプロジェクトコンテキストではなく、再利用可能な多段階のワークフローについては、[agent skill](⟦XYAH⟧)を検討してください。自分でワークフローを作成する前に、[Look for an existing skill in the Customization Marketplace](⟦6Z4X⟧)を探してください。リポジトリ固有のコマンドや規約は、プロジェクトの指示に記述してください。

### 1つのリクエストに指示を添付する

一時的な要件については、共有ルールを作成するのではなく、プロンプトにガイダンスを記述します。

1つのリクエストで既存の指示ファイルを再利用するには、チャット入力欄にある **Add Context**（⟦HVKC⟧ アイコン）を選択し、リクエストを送信する前にそのファイルを選択します。

## 効果的な指示を書く

リポジトリ内のすべてを説明するのではなく、エージェントがプロジェクト固有の決定を下すのに役立つルールを記述します。

| 代わりに | 次のように書く |
|------------|-------|
| 良いテストを書く。 | ⟦WMST⟧ からフィクスチャを再利用し、テストを変更した後に ⟦WJ5W⟧ を実行する。 |
| アーキテクチャに従う。 | HTTP ハンドラーが個別にテスト可能な状態を維持できるよう、データベースアクセスを ⟦D6QC⟧ 内に保持する。 |
| 私たちのスタイルに従う。 | エラー文字列を返すのではなく、⟦XJTQ⟧ 内の既存のエラー型を使用する。 |

* **ルールを簡潔に保つ。** 各要件に対して短い文を使用し、自明ではない制約について説明します。
* **実行可能な詳細を優先する。** エージェントが使用すべきコマンド、ディレクトリ、ライブラリ、または既存の例を指定します。
* **不要なコンテキストを避ける。** フォーマッタやリンターによって強制されるルールを重複させないでください。特化したガイダンスはプロジェクト全体のファイルから移動させます。
* **コードと一緒に指示を保守する。** ソース管理を通じて変更をレビューし、コマンド、アーキテクチャ、または依存関係が変更されたときにルールを更新します。
* **サポートドキュメントを慎重に参照する。** 相対パスと ⟦5C2V⟧ 区切り文字を使用した Markdown リンクを使用します。リンクがあるからといって、ドキュメントの内容がモデルに確実に届くとは限りません。[referenced-file behavior](⟦2K9T⟧)を確認してください。

### 競合する指示を解決する

個人的なガイダンス、リポジトリのガイダンス、および組織のガイダンスの間で、共有要件が一貫していることを確認します。普遍的な優先順位の順序に頼らないでください。[combination rules differ by harness](⟦FZ23⟧)です。

個人的な指示が一方のライブラリを要求し、リポジトリが別のライブラリを要求している場合は、競合する個人的なルールを削除するか、範囲を狭めます。補正するためにもう1つのルールを追加しないでください。競合を解決した後、新しいチャットで同じ代表的なタスクを繰り返します。

## プロジェクトと個人の指示を管理する

既存の指示を見つけて編集するには、Agent Customizations エディタの **Instructions** に戻ります。個人の指示を追加するには、**User** の横にある ⟦FHEK⟧ を選択します。ハーネスがサポートする名前と保存場所のプロンプトに従い、ファイルを保存して、そのハーネスを使用した新しいチャットで検証します。

プロジェクトをまたいだ個人的な好みには、ユーザーの個別のスコープを使用します。チームが求めているのでなければ、個人の応答の好みを共有プロジェクトファイルに入れないでください。場所と同期の制限については、[user instructions](⟦TMH2⟧)を参照してください。

また、関連するエージェント、スキル、ツールとともに、[agent plugin](⟦C5WN⟧)内のルールコンポーネントとして指示を配布することもできます。サポートは、選択したハーネスとプラグインフォーマットによって異なります。クライアント間でバンドルを共有する前に、[plugin compatibility](⟦KCR8⟧)を確認してください。

## 指示のトラブルシューティング

ガイダンスを変更する前に、障害の発生段階を特定します。

| 観察される状況 | 確認すべき点 |
|------------------|---------------|
| ファイルが Customizations エディタに表示されない。 | 選択したハーネス、ファイル名、サポートされている場所、およびセッションが変更内容を含むフォルダを使用しているかどうかを確認します。 |
| ファイルが検出されているが、タスクに含まれていない。 | フロントマターのエラーとアクティベーション条件を確認します。一致するファイルをテストするか、手動で指示を添付します。Local の場合は、適用可能な [discovery settings](⟦5ZSJ⟧)を確認します。 |
| ファイルが含まれているが、結果がそれに従っていない。 | 矛盾しているルールや曖昧なルールがないか確認します。1つのルールを明確にし、新しいチャットでタスクを繰り返し、実際の変更点とツールの動作を比較します。 |

可能であれば、応答の **References** セクションは、コンプライアンスではなくインクルード（包含）を確認するのに役立ちます。詳細な証拠については、[instruction diagnostics](⟦K7D2⟧)に従ってください。問題を再現する前にロギングを準備します。
